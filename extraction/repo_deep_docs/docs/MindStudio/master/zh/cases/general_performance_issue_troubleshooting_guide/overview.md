# 昇腾性能优化简介 — 一体化深度解读

---

## 【定位】

本文档是昇腾AI计算平台上**深度学习系统性能分析与优化框架的总纲性概述**，目的是回答"在昇腾平台上做训练/推理时，性能瓶颈在哪里、应遵循哪些优化原则、以及从哪些维度切入优化"这一根本问题，为后续具体的性能问题排查与优化手段提供原则性指引。

---

## 【技术要点】

1. **优化原则三要素**：算子优先、昇腾亲和优化策略、模型设计策略，三者构成昇腾性能优化的根本准则（原文：表1）。
2. **昇腾硬件亲和性核心数据**：昇腾AI处理器 **Cache Line 大小为 512 字节**，约为业界常见 32 字节的 16 倍，用以提升大粒度数据传输带宽、降低访存延迟（原文：表1"昇腾亲和优化策略"）。
3. **四大优化维度**：计算、通信、下发、服务化推理（原文：表2）。
4. **计算维度的关键指标**：矩阵乘计算利用率、MTE 搬运流水利用率、Cube 资源使用率，并需消除 AI CPU 算子和非亲和算子，充分利用融合算子（原文：表2"计算"行）。
5. **通信维度的关键要求**：通信带宽达标且无重传；多卡时间均衡无快慢卡；通算并行以掩盖通信延迟（原文：表2"通信"行）。
6. **下发与服务化推理关键指标**：Free 占比尽可能小、调度时间可被计算掩盖、IO/内存问题消除；推理时延逼近纯模型性能、Batch 间 CPU 任务占比最小化、显存占满以最大化吞吐（原文：表2"下发"行、"服务化推理"行）。

---

## 【关键机制与数据】

**性能瓶颈的转移趋势（原文）：** 随着模型规模扩大与场景复杂化，瓶颈从"算力"转移到"Host-Device 协同效率、关键算子性能、通信延迟、模型下发效率"四方面的**协同效率**。

**优化闭环逻辑（原文）：** 性能优化框架涵盖五个环节——性能数据采集 → 算子层优化 → 调度策略调整 → 通信机制改善 → 模型编译下发。这是一条**全流程、系统化**的优化链路。

**昇腾亲和性硬件机制（原文）：**
- 架构特征：**高度并行**，在**指令级并行**与**数据搬运效率**上做了深度优化；
- 数据访问单元：**Cache Line = 512 字节**（vs 业界 32 字节）；
- 优化含义：编程与算子优化应"对齐硬件特性、提升数据局部性、加大单次内存操作规模"，从而吃满高带宽与大吞吐。

**模型设计层原理（原文）：** 模型应**多利用矩阵运算**、**充分复用 AI Core（矩阵计算单元）**——即把负载尽量集中到 Cube 单元，而非散落到 Vector 或 AI CPU。

**计算维度细化目标（原文）：**
- 算子性能符合预期：矩阵乘计算利用率 + MTE 搬运流水利用率达标；
- 计算集中于 AI Core，充分利用 Cube；
- 消除 AI CPU 算子与非亲和算子；
- 充分利用融合算子。

**通信维度细化目标（原文）：**
- 带宽达标、无重传；
- 多卡时延均衡（无快慢卡）；
- 通算并行（通信被计算掩盖）。

**下发维度细化目标（原文）：**
- Free 占比尽可能小；
- 计算掩盖调度时间；
- IO/内存问题消除。

**服务化推理细化目标（原文）：**
- 推理时延逼近纯模型性能；
- Batch 间 CPU 任务占比最小化；
- 在时延约束下、显存占满以最大化吞吐。

## 【表格解读】

### 表1 性能优化原则（原文逐字还原）

| 原则名称 | 说明 |
| --- | --- |
| 算子优先 | 算子能力是基础，唯有优秀的算子能力才能保障单机和集群性能的卓越表现。 |
| 昇腾亲和优化策略 | 昇腾AI处理器基于高度并行的架构设计，在指令级并行和数据搬运效率方面进行了深度优化。例如，在数据访问单元设计上，昇腾的Cache Line大小达到512字节，显著高于业界常见的32字节水平，能够有效提升大粒度数据传输的带宽利用率，降低访存延迟。因此，在编程与算子优化过程中，建议尽可能对齐硬件特性，提升数据局部性，使每次内存操作处理更大规模的数据，从而充分发挥高带宽、大吞吐的优势。 |
| 模型设计策略 | 模型应尽可能多地利用矩阵运算，并充分复用AI Core（矩阵计算单元），以提升整体效率。 |

**逐行解读：**

- **算子优先**：定位为"基础"——意即无论上层调度与通信做得多好，**底层算子效率**是单机/集群性能的天花板。本原则为后续"算子层优化"提供优先级正当性。
- **昇腾亲和优化策略**：给出**硬件事实**（Cache Line 512B vs 业界 32B，约 16× 差距），并由此推导出**编程/算子优化动作**——对齐硬件、提升数据局部性、放大单次访存粒度。逻辑链为：硬件特征 → 编程适配 → 带宽/延迟收益。
- **模型设计策略**：从**算子/硬件层上升到模型层**，强调用矩阵运算（而非通用标量/向量运算）把负载集中到 AI Core 的矩阵计算单元，本质是"以架构特征倒推模型表达"。

### 表2 性能优化方向（原文逐字还原）

| 维度 | 优化方向 |
| --- | --- |
| 计算 | • 算子性能符合预期 (矩阵乘计算利用率，MTE搬运流水利用率等)。<br>• 计算集中于AI Core，充分利用Cube资源。<br/>• 消除AI CPU算子和非亲和算子并进行算法逻辑优化。<br/>• 充分利用融合算子。 |
| 通信 | • 通信带宽符合预期，未发生通信重传等问题。<br/>• 各卡通信时间相对均衡，无明显快慢卡问题。<br/>• 通算并行，计算尽可能掩盖通信时间。 |
| 下发 | • Free占比尽可能小。<br/>• 计算掩盖调度时间。<br/>• IO/内存问题消除。 |
| 服务化推理 | • 模型推理部分时延逼近纯模型性能。<br/>• 最小化Batch间CPU任务占比。<br/>• 调优调度参数和batch上限，在时延约束下显存占满最大化吞吐。 |

**逐行解读：**

- **计算**：从"算子指标 + 硬件资源利用 + 负向算子清理 + 融合算子"四个角度同时施力。其中"矩阵乘计算利用率、MTE 搬运流水利用率"是昇腾特有的两个核心微观指标，分别对应**算**和**搬**两条流水。
- **通信**：从"带宽质量 + 多卡均衡度 + 通算重叠"三个角度评估。重点是**无重传**（传输质量）、**无快慢卡**（集合通信同步效率）、**通算并行**（流水线化）。
- **下发**：聚焦**调度环节本身的开销**——"Free 占比小"意味着调度器繁忙而非空闲等待；"计算掩盖调度"意为把模型下发与一次计算 overlap；"IO/内存问题消除"则是数据通路质量。
- **服务化推理**：面向**在线服务场景**，核心是三件事——**纯计算时延**（去除服务化框架开销后剩余的真实计算时间）、**CPU 侧调度占比**（Batch 间隔的 CPU 占用越小越好）、**吞吐–时延–显存三角权衡**（时延约束下用尽显存以拉满 batch，从而最大化吞吐）。
