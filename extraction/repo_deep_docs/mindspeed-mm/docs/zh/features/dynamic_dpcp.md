# Dynamic DP/CP switch · 深度解读

## 【定位】

这篇文档描述的是 mindspeed-mm 中的**动态 DP/CP 切换（Dynamic DP/CP switch）特性**——解决动态数据集训练中"长短序列并存导致静态 CP 策略下短序列计算效率严重劣化"的问题，核心能力是**每轮迭代依据当前 DP 域数据尺寸实时选定 DP×CP 并行组合并完成并行组热切换与数据再分发**。

---

## 【技术要点】

1. **问题根源**：静态并行策略以"数据集最长序列"为基准确定 CP 度，长序列少而短序列多时，CP 偏大导致短序列也要做 CP 切分，计算效率下降；长短差距越大劣化越严重。
2. **方案核心**：每轮迭代根据每个 DP 实际拿到的数据长度，遍历预生成的并行组列表，挑选"满足序列长度约束"的最优并行策略（**DP 优先**），并同步完成数据分发与并行组切换。
3. **并行组初始化**：在 Megatron 初始化之后，依据用户配置的 `max_cp_size` 自动生成全部候选并行组。例如 `CP=4` 时候选组为 `{dp4cp1, dp2cp2, dp1cp4}`。
4. **数据获取约定**：开启动态 DPCP 后，数据 dataloader 默认按 **DP_nCP_1** 方式取数据；每轮迭代 gather 所有 DP 域的样本尺寸后再决定本轮策略。
5. **并行域热切换**：确定新策略后，修改并行组全局变量指向新的并行组；DP→CP 切换过程中需要执行数据广播，被广播的卡需要**缓存本卡已获得的样本**，后续训练优先从缓存区读取样本数据。
6. **当前约束**：仅支持 **Ulysses 序列并行**；暂不支持 **encoder DP** 与 **interleaved offload**（直接源自参数 `use_dynamic_dpcp` 的说明）。

---

## 【关键机制与数据】

**工作原理（按一次迭代的时间顺序，原文逻辑链）：**

1. **初始化阶段**（一次性）：Megatron 初始化结束后，依据 `max_cp_size` 自动展开候选并行组列表——原文："在megatron初始化之后，使用用户配置的最大CP并行度自动生成并行组列表"。
2. **取数阶段**（每轮迭代）：dataloader 按 `DP_nCP_1` 方式从每个 DP 域拉取样本——原文："数据dataloader默认按照DPnCP1的方式获取数据"。
3. **决策阶段**（每轮迭代）：gather 所有 DP 域的样本尺寸，遍历候选并行组，按"满足序列长度约束"且**DP 优先**的规则选定最优 `DPxCPy`——原文："遍历并行组，得到满足序列长度要求的最佳并行策略(DP优先)"。
4. **切换阶段**（每轮迭代、命中非默认组时）：修改全局并行组变量指向新组；若为 DP→CP 方向的切换，须广播样本数据——原文："修改并行组的全局变量，指向新的并行组。同时从DP到CP切换过程中，需要进行数据广播"。
5. **缓存复用阶段**（持续的本地优化）：被广播过的卡维持本地样本缓存，后续优先吃缓存——原文："被广播的卡需要缓存本卡已经获得的样本，在后续的训练中，优先从缓存区获取样本数据"。

**数值锚点（原文数字/示例）：**
- CP 度上限示例：`CP=4` → 候选组 `{dp4cp1, dp2cp2, dp1cp4}`。
- `max_cp_size=4` → 候选组 `{dp4cp1, dp2cp2, dp1cp4}`（同上一条，是同一示例的复用）。
- 最长视频形态示例：(23×1080×720)，单位为 `(fps, h, w)`。
- 适配版本：opensoraplan1.3。

**性能数据：** 原文未涉及具体加速比/吞吐/显存数字，因此不在此臆造。

## 【表格解读】

> 原文无独立的"配置项矩阵表"以外的表格；下面将"使用方法"中的参数表**逐字还原**并逐行解读：

| 参数名 | 参数含义 |
| --- | --- |
| `use_dynamic_dpcp` | 动态DPCP特性开关，当前仅支持Ulysses序列并行，且暂不支持encoder DP/interleaved offload |
| `max_cp_size` | 集群支持最大的CP并行度, e.g. max_cp_size=4则并行组可为{dp4cp1,dp2cp2,dp1cp4} |
| `max_seq_size` | 设定单卡可以计算的最大序列长度，e.g.最长视频为(23x1080x720)(fps,h,w) |

**逐行解读：**

- **`use_dynamic_dpcp`**：这是**总开关**，打开后才会进入"gather 尺寸 → 遍历并行组 → 热切换 → 广播/缓存"的动态流程。同时它还**硬性约束了功能边界**——目前只能跑在 Ulysses 序列并行之上，且与 encoder DP、interleaved offload 互斥；在这些并存场景下需要保持关闭或先做适配改造。
- **`max_cp_size`**：决定了**候选并行组列表的"上界"**，从而决定 DP/CP 之间能切多少档。例如 `max_cp_size=4` 时可选 `{dp4cp1, dp2cp2, dp1cp4}`——也就是说每轮迭代就是在这一组候选项里挑一个最匹配的策略。设置过大可能造成无意义的搜索开销，过小则粒度不够细、对长短差距大的数据收敛不到最优档。
- **`max_seq_size`**：定义了**单卡可承载的最大序列长度阈值**——这是每轮迭代"是否需要升 CP 来防止 OOM"的判定基准。原文以"(23×1080×720), (fps, h, w)"作为示意最长视频形态，说明该参数并非只看 token 数，还需把视频的帧率×高×宽这类多模态形态映射成等效序列长度后再与阈值比较。配置时该值必须与硬件显存能力以及 `max_cp_size` 联合定档，否则会出现"理论撑得住但实际 OOM"或"早早升 CP 导致短序列被拖累"两种相反方向的劣化。

## 【关联】

> 用户提供的内部链接列表为"(无)"，以下关联仅依据本档正文自带的引用关系给出：

- **与 Megatron 并行初始化流程的耦合点**：本特性在"Megatron 初始化之后"才生成候选并行组列表，意味着其生命周期**叠加在 Megatron 的固有 DP/CP 域之上**，并不替换底层集合通信原语。
- **与数据 dataloader 的契约**：dataloader 被要求"默认按 `DP_nCP_1` 方式获取数据"，也就是说动态 DPCP 把**取数策略与并行组切换解耦**——先按最大粒度取数，再决定如何切。这与 Megatron 默认的 dataloader 假设紧耦合，因此该特性仅在 `use_dynamic_dpcp` 开启后接管取数行为。
- **与 Ulysses 序列并行的依赖**：原文明确"当前仅支持Ulysses序列并行"。这暗示 mindspeed-mm 内部对 CP 至少有 Ulysses 与其他实现（如传统 CP Ring）路径，本特性目前只跑通 Ulysses 一条路径；启用前需确认 CP 后端实装的是哪一条。
- **互斥/暂不支持项**：`encoder DP` 与 `interleaved offload` 在本特性下暂不支持——这三者之间存在功能栅栏，启用动态 DPCP 时要么不勾选另两项，要么后续需等待适配。
- **跨帧/跨卡的样本缓存**：被广播的卡需要"缓存本卡已经获得的样本"，并"优先从缓存区获取样本数据"。这是与采样器/缓冲区的耦合关系——意味着上游采样需要在多轮间保持**样本可复现性**（已拿到的样本不能被覆盖或丢弃），否则缓存命中会读到陈旧数据。
- **版本基线**：标注适配 `opensoraplan1.3`，表明与 opensoraplan 的训练调度/数据流水线版本强相关，升级框架版本时需同步回归本特性。
- **多模态形态的扩展性**：`max_seq_size` 以视频 `(fps, h, w)` 为示例，提示本特性面向的是**多模态生成（T2V，参数文件名 `pretrain_t2v_model.json` 已佐证）**场景下的序列长度动态化，并非纯 NLP 的 token 级调度；扩展到文生图、文生音频等其他模态时需重新校准"等效序列长度"的换算。

## 【使用方法】

**入口位置（原文）：** `pretrain_t2v_model.json`。

**启用方式（依据原文参数表整合）：**

1. 在 `pretrain_t2v_model.json` 中将 `use_dynamic_dpcp` 置为开启。
2. 配置 `max_cp_size`，明确集群支持的 CP 最高并行度（同时也是候选并行组枚举的上界，例如 `4` → `{dp4cp1, dp2cp2, dp1cp4}`）。
3. 配置 `max_seq_size`，表示单卡可计算的最大序列长度（如以最长视频 `(23×1080×720), (fps, h, w)` 为参考校准）。
4. 确认 CP 后端为 **Ulysses 序列并行**，并临时关闭 `encoder DP` 与 `interleaved offload`（原文标注当前不支持）。
5. 框架版本需与 `opensoraplan1.3` 对齐。
