# EP Balance Strategy 文档深度解读

## 【定位】

本特性文档描述 mindspeed-mm 中面向 MoE 模型专家并行（EP）训练场景的**运行时负载均衡方案**，通过在每个 EP Rank 上预留冗余专家槽位并基于贪心策略动态复制热点专家，缓解路由不均导致的"快慢卡"与 OOM 风险。

---

## 【技术要点】

1. **冗余专家 + 动态贪心调度**：在每个 EP Rank 上预留少量冗余专家槽位作为"弹性缓冲池"，系统基于全局实时负载状态，采用贪心策略识别高负载 Rank 上的"热点专家"，并将其动态复制到低负载 Rank 的冗余槽位中。
2. **通信掩盖优化**：利用 `permute` 与 `unpermute` 的反向计算过程，分别掩盖冗余专家**参数同步**与**梯度聚合**产生的通信延迟，避免额外开销暴露在关键路径上。
3. **求解加速**：在 CPU 侧采用 `Numba` 即时编译（JIT）技术加速负载重规划的求解过程，确保调度决策不成为训练性能瓶颈。
4. **早停策略**：求解过程（专家重排与 token 重分配）内置早停策略，使负载本就均衡的场景下性能不会明显劣化（原文表述："性能一般不会有明显的劣化"）。
5. **非确定性副作用**：反向涉及冗余专家梯度累加，**不保证二进制对齐**，故不适用于要求严格确定性训练的场景。
6. **配置开关默认关闭**：`enable_ep_balance` 默认 `false`，需显式开启，且依赖模型 yaml 中存在 `ep_balance_plan` 字段（目前仅个别模型适配）。

---

## 【关键机制与数据】

### 工作原理（调度决策 + 执行优化双层）

原文将机制拆为两个层次协同解决负载不均：

- **调度决策层（算法侧）**：每个 EP Rank 预留**少量冗余专家槽位**→形成弹性缓冲池→基于**全局实时负载**→贪心识别热点专家→动态复制到低负载 Rank 的冗余槽位。Token 因此可从积压 Rank 迁移到空闲 Rank 处理。原文未给出冗余专家数量的具体默认计算公式，仅通过 yaml 中 `max_dup_experts_num` 让用户按 EP size 与总专家数调整。
- **执行优化层（运行时侧）**：
  - 正向 `permute` 与反向 `unpermute` 计算用于**掩盖**参数同步与梯度聚合的通信开销（原文强调"分别掩盖"——可推断正向 mask 参数广播，反向 mask 梯度聚合）。
  - CPU 侧 `Numba` JIT 加速**负载重规划求解**，保证调度决策本身不成为瓶颈。

### 适用条件（收益边界）

- 原文定性描述：
  - **负载显著不均衡** → 收益明显；负载本已均衡 → 收益不明显。
  - **`mbs * seqlen` 较大** → 收益可覆盖求解开销；过小 → 有性能劣化风险（求解复杂度"只和专家数量有关"，与 token 总量解耦，故小 batch 下收益不抵成本）。
- 原文**未给出**任何具体的性能数字（如加速比、显存节省百分比、实测 mbs/seqlen 阈值）。原文亦**未给出**实现图（仅有引用图片 `../../../sources/images/ep_balance.png`，未在原文 markdown 中渲染）。

### 数据流（基于原文描述重建）

```
全局实时负载状态 → 贪心算法识别热点专家 → 在低负载 Rank 的冗余槽位复制专家
        ↓                                                    ↓
   Numba JIT 加速求解                              Token 从高负载 Rank 迁移
        ↓                                                    ↓
   permute 掩盖参数同步                           低负载 Rank 处理被迁移的 Token
        ↓                                                    ↓
   unpermute 掩盖梯度聚合                          梯度通过冗余槽位反向聚合
```

## 【使用方法】

### 配置项（原文 yaml 片段）

```yaml
# ep balance
enable_ep_balance: false
ep_balance_plan:
    max_dup_experts_num: 2
```

字段说明（直接引自原文）：

| 字段 | 含义 | 取值/建议 |
|---|---|---|
| `enable_ep_balance` | 是否开启该负载均衡策略 | 默认 `false`，开启需改为 `true` |
| `max_dup_experts_num` | 每个 EP Rank 可分配的冗余专家数量上限 | 建议根据 **EP size** 与**总专家数**调整 |

### 启用流程（基于原文推断）

1. 确认目标模型的 `.yaml` 配置文件中已包含 `enable_ep_balance` 与 `ep_balance_plan` 字段（原文："适配了该方案的模型会在模型的 `.yaml` 配置文件中找到以下字段"）。
2. 将 `enable_ep_balance` 设置为 `true`。
3. 按 EP size 与总专家数调整 `max_dup_experts_num`（原文未给出推荐公式）。

### 推荐场景（原文）

1. 开启 EP 后**存在严重负载不均衡**。
2. `mbs * seqlen` 较大的训练场景。

### 不推荐场景（原文）

- **需要严格确定性训练的场景**：因反向涉及冗余专家梯度累加，**不保证二进制对齐**。

### 启用后预期效果（原文）

- 各节点计算负载趋于平衡，缓解"快慢卡"问题。
- 减少因极度负载不均衡导致的 **OOM 风险**。
