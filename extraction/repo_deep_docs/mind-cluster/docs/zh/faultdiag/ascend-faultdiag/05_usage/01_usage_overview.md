# 深度解读：ascend-fd 特性概览

## 【定位】

本篇文档为 ascend-fd（Ascend Fault Diagnosis，昇腾故障诊断组件）的能力总览页，明确告知用户该组件在使用前的环境约束（文件描述符/系统时间/管道命令注意事项）、所支持的任务规格（仅整机满卡）、各类日志的版本配套关系，并列出全部子特性入口，作为进入各子功能文档的索引与导读。

## 【技术要点】

1. **集群规模与系统限制联动**：Linux 默认单进程文件描述符上限为 1024，因此 ascend-fd 推荐的诊断集群规模为不超过 128 台服务器（约 1024 卡）；超过该规模需使用 `ulimit -n <值>` 调整上限，否则会触发诊断失败。
2. **命令调用限制**：执行 ascend-fd 命令时需避免管道（如 `xxx | yyy` 等），因为管道可能干扰用户 IP 的获取和日志审计，影响故障定位准确性。
3. **任务范围限定**：ascend-fd 仅对"整机满卡"训练或推理任务提供故障诊断，非满卡场景可能造成根因定位错误或失败。
4. **时间一致性要求**：三组时间必须同步——各服务器之间系统时间一致、每台服务器 Host 与 Device 系统时间一致、宿主机与容器（如在容器中执行任务）的系统时间一致，否则分析结果不可靠。
5. **日志版本配套矩阵**：对 Host/Device 应用日志（CANN）、PyTorch 框架、MindSpore 框架、Host OS、Device 侧（HDK）、MindCluster 组件（Device Plugin/NodeD/Volcano 等）、MindIE 组件（Server/LLM/SD/RT 等）、AMCT 模型压缩、PyMotor/vLLM 等九类日志，均有对应的最低软件版本要求。
6. **11 项子特性入口覆盖完整工作流**：从日志采集 → 日志清洗 → 故障诊断 → 单机/超节点诊断 → 自定义实体/日志屏蔽/配置 → 三类 SDK 接口化能力，构成 ascend-fd 端到端能力矩阵。

## 【关键机制与数据】

- **文件描述符约束推导**（原文）：Linux 系统最大文件描述符数默认 1024，因此"集群规模建议不超过 128 台服务器（1024 卡）"。两者的对应关系由原文直接给出（128 台 × 每台约 1 卡节点规模推算）。
- **三类时间同步链路**（原文）：服务器间 → Host↔Device → 宿主机↔容器，构成三层嵌套同步链，任一层缺失都会导致"分析结果不准确"。
- **命令行为约束**（原文）：管道命令会阻塞"用户 IP 获取"和"日志审计"两类功能，属于隐式联动机制，原文未给出更细粒度原理。
- **任务规格约束**（原文）：满卡是根因定位正确性的前提条件，原文表述为"可能导致故障根因定位错误或失败"，未给出量化错误率。

**逐行解读：**

- **CANN 应用类日志**：覆盖 Host 与 Device 两侧应用类日志，要求 CANN ≥ 7.0.RC1，是 ascend-fd 识别应用层异常的最基础数据源。
- **PyTorch 框架日志**：由 PyTorch 适配插件产出，要求适配插件 ≥ 5.0.RC3，原文未对说明列作补充。
- **MindSpore 框架日志**：要求 MindSpore ≥ 2.1.0，且说明列明确"部分故障有特定版本要求"——意味着存在按 MindSpore 版本区分的故障子集，需查阅具体故障文档版本说明。
- **Host OS 日志**：列出四个具体操作系统版本（CentOS 7.6、Debian 10.0、EulerOS 2.10/2.12、CTyunOS 22.06），并对日志体量给出量化建议——"建议日志大小 512MB 以内"，避免过大日志拖慢清洗和诊断效率。
- **Device 侧日志**：依赖 Ascend HDK ≥ 23.0.RC3，覆盖 Device 自身固件/驱动层异常。
- **MindCluster 组件日志**：要求 6.0.RC3 及以上，涉及 Ascend Device Plugin、NodeD、Volcano 等调度与节点管理组件，构成多组件协同诊断对象。
- **MindIE 组件日志**：要求 6.0.0 及以上，覆盖 MindIE Server、LLM、SD、RT 等推理服务组件。
- **AMCT 组件日志**：针对模型压缩场景，要求 AMCT ≥ 7.0.RC1，原文无补充说明。
- **PyMotor/vLLM 日志**：要求 MindIE-PyMotor 与 vLLM ≥ 26.1.0，原文无补充说明；版本号明显高于其他行，提示该集成较新。

**逐行解读（按数据流先后顺序）：**

- **日志采集 → 日志清洗 → 故障诊断**：构成核心数据处理流水线，先收集、再提取、最后归因，是通用排障路径。
- **单机故障诊断**：作为完整诊断流程的轻量子集，定位"单台设备"场景，强调"快速"诊断能力。
- **超节点故障诊断**：专用于 Atlas A3 超节点这一特殊硬件形态（区别于常规 N 节点集群），是平台定制化能力。
- **自定义故障实体**：用户可在内置规则之外追加自定义检测规则，属于扩展点。
- **屏蔽故障日志 / 自定义配置文件**：均属"可调行为"侧——前者过滤（屏蔽）噪音日志，后者调整清洗与诊断的执行策略（配置项）。
- **三类 SDK 接口**：业务日志清洗、根因节点清洗及诊断、故障事件清洗及诊断，将同一套能力通过 SDK 对外开放，覆盖"清洗数据"+"诊断分析"两种操作，便于用户把 ascend-fd 能力集成进自有系统。

## 【使用方法】

以下为原文中明确出现的启用/配置方式：

1. **调整文件描述符上限（针对大规模集群）**：
   - 命令：`ulimit -n <值>`
   - 触发条件：集群规模超过 128 台服务器（约 1024 卡）时，需调高 Linux 默认 1024 的文件描述符上限。
   - 失败排错详见：[集群规模较大时诊断失败](../07_references/02_faq.md#集群规模较大时诊断失败)。

2. **任务格式前置条件**：
   - 须为"整机满卡"训练或推理任务；非满卡场景原文建议不要执行诊断。

3. **系统时间同步（启用诊断前必做）**：
   - 服务器之间时间同步。
   - 每台服务器 Host ⇄ Device 系统时间同步。
   - 容器化场景下，宿主机 ⇄ 容器系统时间同步。

4. **命令调用规范**：
   - 执行 ascend-fd 命令时不要使用管道命令，避免影响用户 IP 获取与日志审计。

5. **日志版本配套**：
   - 按"日志版本配套表"核对 9 类日志与其对应软件的版本要求；其中 Host OS 日志建议控制在 512MB 以内。

6. **功能级入口**：本文未给出 `ascend-fd` 的具体启动命令与配置项；具体启用方式请进入各子特性文档（日志采集、日志清洗、故障诊断等）查阅。
