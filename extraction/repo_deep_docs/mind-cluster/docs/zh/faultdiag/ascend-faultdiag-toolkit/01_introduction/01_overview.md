# 深度解读：ascend-fd-tk 概述文档

---

## 【定位】

本文档定位为 MindCluster 体系中 **ascend-fd-tk（昇腾集群链路故障诊断工具）** 的入门概述文档，向用户说明该工具的能力边界、适用场景、支持环境与标准使用流程，作为后续配置、操作与排障章节的引子。

---

## 【技术要点】

基于原文，可提炼以下核心机制要点：

1. **双模式运行**：ascend-fd-tk 提供**交互式**与**非交互式**两种操作模式，覆盖不同使用习惯与自动化集成需求。
2. **双数据处理能力**：具备**在线数据自动采集**与**离线日志清洗**两种数据处理路径，可适配实时排障与事后分析两类场景。
3. **多设备覆盖**：诊断链路覆盖 **服务器、L1/L2 灵衢交换机、RoCE 交换机、BMC** 四类设备信息，作为故障定位的输入源。
4. **连接方式适配**：在线采集依据配置的集群设备（服务器 / BMC / 交换机）连接信息，支持**账号、密码 / 密钥 / 免密**三种认证形态，并通过 **SSH** 自动完成数据采集。
5. **分批采集与汇总诊断**：支持多网络平面场景下**分批采集**设备信息，再**汇总统一诊断**，适合大规模、多拓扑集群。
6. **缓存清理规范**：原文明确要求每次使用工具前执行 `clear_cache` 清理缓存，避免上一任务的残留数据污染本次诊断结果。

---

## 【关键机制与数据】

### 工作原理（按原文梳理）

- **在线模式链路**：依据连接文件（账号 / 密码 / 密钥 / 免密）→ SSH 访问服务器、BMC、交换机 → 自动采集原始日志 → 清洗 → 诊断 / 巡检 → 生成报告。
- **离线模式链路**：导入已落盘的 **服务器带内日志、BMC dump 日志、交换设备 diagnostic information 日志** → 清洗 → 诊断 / 巡检 → 生成报告。
- **报告输出位置**：诊断 / 巡检完成后，报告**自动生成至家目录下的 `report` 子目录**（依据内部链接 `../05_usage/01_usage_overview.md` 所指引的章节进一步说明）。

### 关键性能 / 数据相关说明

- 原文未提供具体性能指标（如采集耗时、并发上限、报告大小等），仅描述功能层面能力，**不臆造数字**。
- 原文提及 **"巡检特性是 beta 特性，不建议在正式环境中使用"**，且在「操作系统」表中同样标注 Windows 支持为 **beta 特性**——这两处是文档中显式的可用性 / 成熟度提示。

## 【表格解读】

原文包含两张关键表格，逐字还原并逐行解读如下。

### 表 1：核心能力

| 能力 | 说明 |
|------|------|
| 在线采集与清洗 | 根据配置的集群设备（服务器、BMC、交换机）连接信息（账号、密码 / 密钥 / 免密），自动通过 SSH 采集数据并完成信息清洗 |
| 离线日志清洗 | 导入已采集的服务器带内日志、BMC dump 日志和交换设备 diagnostic information 日志，进行信息清洗 |
| 一键诊断 | 自动完成信息采集与故障诊断，生成诊断报告 |
| 分批采集与统一诊断 | 支持多网络平面场景下分批采集设备信息，汇总后统一诊断 |
| 客户定制化巡检 | 支持按客户类型定制诊断规则进行巡检（巡检特性是 beta 特性，不建议在正式环境中使用。） |

**逐行解读：**
- **在线采集与清洗**：依赖**预先配置的设备连接信息**作为前置条件，三种认证形态（账号密码 / 密钥 / 免密）覆盖了主流运维场景；数据搬运通道为 **SSH**。
- **离线日志清洗**：明确了离线模式的三类原始日志来源——**服务器带内日志**、**BMC dump 日志**、**交换设备 diagnostic information 日志**，对应在线采集的三类设备来源。
- **一键诊断**：把"采集 + 诊断 + 出报告"打包为单步流程，降低使用门槛。
- **分批采集与统一诊断**：解决大规模、多网络平面集群一次性采集受限的问题，是面向"分批 + 汇总"流程的关键能力。
- **客户定制化巡检**：支持按客户类型定制诊断规则，**原文明确标注其为 beta 特性、不建议用于正式环境**。

### 表 2：操作系统支持

| 操作系统 | 版本要求 | 架构 | 说明 |
|----------|---------|------|------|
| Linux | CentOS 7.6+ / Ubuntu 18.04+ / openEuler 20.03+ | x86_64 / aarch64 | 推荐 |
| Windows | Windows 10 / Windows 11 | x86_64 | 特性是 beta 特性，不建议在正式环境中使用 |

**逐行解读：**
- **Linux 行**：三种发行版均设最低版本阈值（CentOS 7.6+、Ubuntu 18.04+、openEuler 20.03+），同时覆盖 **x86_64 与 aarch64 两种架构**，并被标注为 **"推荐"**，表明生产 / 测试优先选择此组合。
- **Windows 行**：覆盖 **Windows 10 / 11**，仅支持 **x86_64** 架构，且原文标注其为 **beta 特性**，不建议用于正式环境——属于"有但不推荐"的扩展项。

## 【使用方法】

依据原文「使用流程」一节，标准化使用步骤如下（**全部来自原文**，未补充推测）：

1. **安装工具**：通过 **Whl 包**完成工具安装。
2. **配置文件设置（可选）**：提供机房位置等附加配置信息。
3. **配置数据源 / 设置日志路径**：
   - 在线模式 → 配置连接文件；
   - 离线模式 → 设置日志目录。
4. **日志清洗**：
   - 在线模式 → 自动收集设备日志并清洗；
   - 离线模式 → 直接清洗日志信息。
5. **诊断 / 巡检**：对清洗后的数据进行故障诊断或巡检。
6. **查看报告**：诊断 / 巡检完成后，报告自动生成至家目录下的 `report` 子目录（详见 `../05_usage/01_usage_overview.md`）。

**强制规范（原文 NOTE 强调）**：

> 每次使用工具前，建议先执行 **`clear_cache`** 清理缓存，以避免上一次诊断任务的残留数据影响本次诊断结果。
