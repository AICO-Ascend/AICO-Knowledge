# ParaKV 架构设计文档深度解读

## 【定位】
本篇文档是 ParaKV 的**系统架构综述文档**，用以阐述 ParaKV 的产品定位（LLM KVCache 与推荐场景的参数服务器存储）、单实例四层系统架构（存储引擎 / 传输引擎 / 接口层 / 管理层），以及基于 Redis Cluster 风格哈希槽的去中心化集群管理与扩缩容方案。

---

## 【技术要点】

1. **双重部署形态**：ParaKV 既支持 **embedded 嵌入模式**（直接集成到推理引擎或参数服务器内部），也支持**独立集群模式**（作为可横向扩展的持久化存储集群）。
2. **单实例四层分层架构**：自下而上分为**存储引擎**（SSD / 内存介质，索引/数据/老化）、**传输引擎**（TCP / RDMA 通道，KeepAlive 自动选路）、**接口层**（CRUD + 版本管理 + 故障恢复 + 负载均衡）、**管理层**（集群管理 / 服务发现 / 主从复制 / 告警监控）。
3. **去中心化集群管理**：借鉴 **Redis Cluster 哈希槽**方案进行集群管理，便于动态扩缩容。
4. **固定 16384 哈希槽**：每个 key 经 **CRC16 校验后对 16384 取模**决定所属槽位，由集群节点分段负责（如三节点示例：0-5500 / 5501-11000 / 11001-16384）。
5. **在线无损扩缩容**：槽位迁移在节点间进行**不停服**，保证集群可用性的同时实现节点加入与移除。
6. **多传输通道与高可用**：传输引擎同时支持 **TCP 与 RDMA**，并由 **KeepAlive** 机制自动选择路由，接口层承担故障恢复和负载均衡。

---

## 【关键机制与数据】

### 工作原理
- **存储引擎**：作为数据持久化层，向上提供索引与数据访问能力，向下对接 SSD、内存等多种介质，并内建数据老化（TTL/淘汰）能力，支撑 KVCache 这类大对象存取与生命周期管理。
- **传输引擎**：抽象出统一的传输通道抽象，**同时支持 TCP 与 RDMA**；**KeepAlive 机制**用于探测链路健康状态并据此自动选择可用路由，从而在不同网络环境下取得性能与可靠性的平衡。
- **接口层**：向上提供**增删改查（CRUD）**；针对**参数服务器场景**额外提供**版本管理**能力，便于模型参数的多版本切换与回滚；针对传输引擎提供**故障恢复**与**负载均衡**。
- **管理层**：负责**集群管理、服务发现、主从复制、告警监控**，为整体系统提供控制面能力。

### 集群数据流（哈希槽定位）
- 写入/读取时，客户端用 **CRC16(key) mod 16384** 计算得到槽号；
- 根据槽号 → 节点映射表定位目标节点；
- 请求命中本节点则本地处理，否则转发至目标节点；
- 当集群拓扑变化（新增/删除节点）时，仅需**迁移部分哈希槽**，迁移过程不停服，集群持续可用。

### 性能/容量数据
- 原文：**哈希槽总数 = 16384**；三节点示例**槽位划分 = 0-5500 / 5501-11000 / 11001-16384**（原文："比如当前集群有3个节点，那么节点A包含0到5500号哈希槽，节点B包含5501到11000号哈希槽，节点C包含11001到16384号哈希槽"）。
- 原文未给出吞吐、延迟、容量等量化性能数据。

## 【公式解读】

原文以文字形式给出哈希槽定位规则，未显式列出 LaTeX 公式，但包含一个可被还原的算式：

$$
\text{slot} = \text{CRC16}(\text{key}) \bmod 16384
$$

**符号逐项说明**：
- `CRC16(key)`：对 key 进行 **CRC-16 校验**，得到 16 位散列值（与 Redis Cluster 相同的散列方式）。
- `\bmod 16384`：对 CRC16 结果**取模 16384**（即 `2^14`），得到 0–16383 范围内的槽位编号。
- `slot`：最终落点**哈希槽编号**，用于在集群中定位负责该 key 的目标节点。

**作用**：通过把 key 空间均匀映射到固定数量的 16384 个槽，使得节点只需声明自己负责哪些槽即可提供服务；当节点增减时，只需迁移部分槽（而非重新哈希全部 key），从而实现**在线、增量式、停服时间为零**的扩缩容。

## 【关联】

由于本文为综述性架构文档，文末**未提供内部链接**，故无显式上下游引用。但从文档自身可梳理出以下模块/特性之间的内部关联：

- **存储引擎 ↔ 传输引擎**：存储引擎负责"数据放在哪里、怎么老化"，传输引擎负责"数据怎么搬"，二者通过接口层解耦。
- **接口层 → 存储引擎**：CRUD 与**版本管理**（参数服务器场景）直接调用存储引擎能力。
- **接口层 → 传输引擎**：**故障恢复**与**负载均衡**依赖传输引擎的 KeepAlive 选路与 RDMA/TCP 通道。
- **管理层 ↔ 所有层**：集群管理 / 服务发现 / 主从复制 / 告警监控横跨存储、传输、接口三层，构成控制面。
- **单实例架构 ↔ 集群管理**：单实例架构的四层是**节点内**视角；集群管理（哈希槽 + 16384 + CRC16 路由）则是**节点间**视角，二者合起来构成 ParaKV 的完整系统视图。
- **embedded 模式 vs 集群模式**：在同一套四层架构基础上，部署形态二选一——embedded 时直接以库的形式被推理引擎/参数服务器链接进来，集群模式时由多节点协作对外提供持久化 KV 服务。
