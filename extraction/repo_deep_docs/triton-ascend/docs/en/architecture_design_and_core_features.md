## 【定位】

这篇文档系统描述 **Triton-Ascend 的整体架构设计与核心功能**,解决"如何在华为 Ascend NPU(基于 CANN 软件栈)上落地 Triton 这一套 Triton 语言与编译工具链"的问题,具体涵盖逻辑分层、代码组织原则、语言扩展、编译器选项、SIMD 编译器的 Pass 流水线与典型变换机制。

---

## 【技术要点】

1. **三层核心组件(Logical Architecture)**
   - `Ascend language extension`:在标准 Triton 语言之上引入针对 Ascend NPU 的语法/语义扩展。
   - `compiler`:接收上层 Triton 编译器产出的 Triton IR (`TTIR`),做面向 Ascend 硬件的一系列变换。
   - `driver`:提供 Triton runtime 与 Ascend 软件栈(CANN)之间的互连能力,并在设备端加载 BiSheng Compiler 产出的可执行 kernel 文件。

2. **编译流水线(原文关键代码)**
   ```
   Triton IR → Linalg IR → AscendNPU IR → triton_xxx_kernel.o
   ```
   - 由 Triton IR 降到 Linalg IR,再经 BiSheng Compiler 生成 Ascend NPU 上的可执行二进制 `triton_xxx_kernel.o`。

3. **代码组织原则(Code Structure Principles,原文)**
   - 与目标无关(target independent)的修改保留在 **Triton core**(如语言和运行时的通用修改)。
   - 与目标亲和(target affinitive)的修改放在 **Triton-Ascend** 部分。

4. **目录与功能映射**
   - `include/` 与 `lib/`:Ascend NPU 的 MLIR Pass、方言及相关工具,负责在 MLIR 编译流程中表示与优化 Ascend 特定的计算图。
   - `libdevice.py`:面向 Ascend NPU 的 `libdevice` API,由 Triton 算子调用以获取底层硬件支持。
   - `backend/compiler.py`:`triton-ascend` 编译器主入口,把 Triton 高层 DSL 编译成 `.o` 可执行文件。
   - `backend/driver.py`:`triton-ascend` 驱动模块,加载并启动编译产物。

5. **Triton 核心语言扩展(3 个算子)**
   - `tl.insert_slice(full, src, offsets, sizes, strides)`:把源张量按 offset/size/stride 插入目标张量。
   - `tl.extract_slice(full, offsets, sizes, strides)`:按 offset/size/stride 从源张量提取切片。
   - `tl.get_element(source, offset)`:读取指定 offset 的单个元素。

6. **17 个 NPU Compiler Options / Autotune 选项**(详见表格解读)
   - 覆盖:ping-pong pipeline(`multibuffer`)、CV 融合专用开关(`enable_auto_bind_sub_block`、`enable_hivm_auto_cv_balance`、`sync_solver`、`tile_mix_vector_loop`、`tile_mix_cube_loop`、`disable_auto_inject_block_sync`、`enable_nd2nz_on_vector`)、同步/屏障注入(`unit_flag`、`inject_barrier_all`、`inject_block_all`)、多 buffer 限制(`limit_auto_multi_buffer_only_for_local_buffer`、`limit_auto_multi_buffer_of_local_buffer`、`set_workspace_multibuffer`)、stream 选择(`stream`)、线性化(`enable_linearize`)、AutoBlockify(`auto_blockify_size`,需 `TRITON_ALL_BLOCKS_PARALLEL` 已设置才生效)。

7. **SIMD 编译器 Pass 流水线(4 阶段)**
   - `triton-to-structured`(linearize,ttir→ttir)
   - `triton-to-unstructured`(把间接轴转成循环,ttir→ttir)
   - `triton-to-linalg`(memory/reduction/view/creation/math/arith/linear algebra → linalgir,ttir→linalgir)
   - `triton-to-other`(ttir→hivm/hfusion/llvm)

8. **TritonToStructured 的核心变换**
   - 把指针表达式与掩码表达式中的整数除法/取模,转换为张量操作,以重新生成 load/store 等 OP。
   - 两个 Converter:`RewriteAddPtrOp`(解析 `AddPtrOp` 中的指针表达式并建模为 `PtrState` 对象)与 `CreateAddPtr`(基于 `PtrState` 重建新的 `AddPtrOp`,消除原始表达式里的 `//` 与 `%`)。

## 【关键机制与数据】

**整体工作流(原文逐字):**

- **入口与上下游衔接**:`backend/compiler.py` 把 Triton 高层 DSL 编译成 Ascend NPU 上的可执行二进制文件(如 `.o`);`backend/driver.py` 加载并启动该二进制。原文说明 `compiler` 接收的是**上层 Triton 编译器生成的 TTIR**,再交给 BiSheng Compiler 走到 `triton_xxx_kernel.o`。
- **IR 路径(原文)**: `Triton IR → Linalg IR → AscendNPU IR → triton_xxx_kernel.o`,即先把 Triton IR 降到 Linalg IR,再经 BiSheng 生成设备可执行文件。
- **目标分层(原文)**:
  - "If the modification is target independent, it should be retained in the Triton core part (such as general modifications to the language and runtime)."
  - "If the modification is target affinitive, it should be placed in the Triton-Ascend part."
- **驱动定位(原文)**:"Provides the interconnection capability between the Triton runtime and the Ascend software stack (CANN), and loads the executable kernel file `triton_xxx_kernel.o` generated by the BiSheng Compiler on the device side."
- **Pass 入口(原文)**:3.2.2 的 4 行 Pass 表给出 IR 转换方向(`ttir->ttir`、`ttir->linalgir`、`ttir->hivm/hfusion/llvm`)。
- **TritonToStructured 的语义(原文)**:"The integer division and modulo operations in pointer expressions and mask expressions are converted to tensor operations to regenerate OPs such as load and store."
- **RewriteAddPtrOp 的作用**(原文举例):对形如 `ptr + x // 1024 * 4096 + x % 1024 * 4 + y` 的表达式,分析 `x`、`y` 轴的贡献与关系,建模成 `PtrState`。其两条限制(原文):
  1. 原始迭代轴(如 `x`)必须能被拆分轴(如 `1024`)整除。
  2. 外部 `XBLOCK` 的大小必须是拆分轴 `divisor` 的整数倍或因子。

> 原文未给出具体性能数字、吞吐、延迟、编译耗时等数据;文档仅停留在架构、Pass 行为与开关说明层面。

## 【表格解读】

### 表格 1 — 3.1.1 Language Extension(Triton 核心语言扩展)

| No. | Operator | Description |
| :--- | :--- | :--- |
| 1 | `tl.insert_slice(full, src, offsets, sizes, strides)` | Inserts a tensor into another tensor according to the specified offset, size, and stride.<br>**Returns**: target tensor.<br>**full**: target tensor. The source tensor will be inserted into this tensor.<br>**src**: source tensor.<br>**offsets**: offset (integer tuple) on the target tensor.<br>**sizes**: size (integer tuple) on the source tensor.<br>**strides**: stride (integer tuple) on the target tensor. |
| 2 | `tl.extract_slice(full, offsets, sizes, strides)` | Extracts a slice tensor from another tensor according to the specified offset, size, and stride.<br>**Returns**: slice tensor.<br>**full**: source tensor. The slice is extracted from this tensor.<br>**offsets**: offset (integer tuple) on the source tensor.<br>**sizes**: size (integer tuple) of the slice tensor.<br>**strides**: stride (integer tuple) on the source tensor. |
| 3 | `tl.get_element(source, offset)` | Reads a tensor with dimensions and returns a single element at the specified offset.<br>**source**: source tensor.<br>**offset**: offset (integer tuple) of the element to be extracted. |

**逐行解读**

- **Row 1 (`tl.insert_slice`)**:三参量张量插入算子。`full` 是被插入的目标张量,`src` 是源张量,通过 `offsets`(目标轴上起点)、`sizes`(源张量参与写入的尺寸)、`strides`(目标轴上步长)把 `src` 嵌入 `full` 中。返回完整的目标张量。语义上类似 numpy/torch 的 `tensor[index] = src`,但显式参数化 offset/size/stride。
- **Row 2 (`tl.extract_slice`)**:张量切片提取算子。`full` 是被切的对象,`offsets/sizes/strides` 描述从源上如何取一段。返回的是切片张量本身,而非 `full`。
- **Row 3 (`tl.get_element`)**:读取某具体 offset 处的单元素,签名上只有两个参数(`source`、`offset`),语义最简单,适合把一个高维张量按 offset 取出标量。

> 注意:Row 1 与 Row 2 的命名结构差异(`insert_slice` 多一个 `src` 参数,而 `extract_slice` 没有)直接体现了"插入/取出"语义的不同。

### 表格 2 — 3.2.1 Compiler Options(NPU 编译器/Autotune 选项)

| No. | NPU Option | Hardware Platform | Description |
| --- | --------------------------------------------- | ---------- | ----- |
| 1 | multibuffer | NPU | Autotune option. It enables or disables the ping-pong pipeline. |
| 2 | enable_auto_bind_sub_block | NPU | Autotune option (CV-fused kernels only). It enables or disables auto-binding of sub-blocks. |
| 3 | enable_hivm_auto_cv_balance | NPU | Autotune option (CV-fused kernels only). It enables or disables automatic CV balancing. |
| 4 | sync_solver | NPU | Autotune option (CV-fused kernels only). It enables or disables the synchronization solver. |
| 5 | unit_flag | NPU | Autotune option. It enables or disables the sync unit flag. |
| 6 | inject_barrier_all | NPU | Autotune option. It enables or disables automatic injection of barriers for all operations. |
| 7 | inject_block_all | NPU | Autotune option. It enables or disables automatic injection of blocks for all operations. |
| 8 | limit_auto_multi_buffer_only_for_local_buffer | NPU | Autotune option. It restricts automatic multi-buffering only to local buffers. |
| 9 | limit_auto_multi_buffer_of_local_buffer | NPU | Autotune option. It enables or disables automatic multi-buffering for local buffers. |
| 10 | set_workspace_multibuffer | NPU | Autotune option. It enables or disables multi-buffering for the workspace. |
| 11 | tile_mix_vector_loop | NPU | Autotune option (CV-fused kernels only). It enables or disables tiling for vector loops. |
| 12 | tile_mix_cube_loop | NPU | Autotune option (CV-fused kernels only). It enables or disables tiling for cube loops. |
| 13 | disable_auto_inject_block_sync | NPU | Autotune option (CV-fused kernels only). It enables or disables automatic injection of block synchronizations. |
| 14 | stream | NPU | (Optional) Informs the compiler about the NPU stream to use. |
| 15 | enable_linearize | NPU | Autotune option. It enables or disables the linearization pass. |
| 16 | enable_nd2nz_on_vector | NPU | Autotune option (CV-fused kernels only). It enables or disables the ND (n-dimensional) to NZ (non-zero) layout transformation. |
| 17 | auto_blockify_size | NPU | Autotune option. It enables or disables AutoBlockify pass. It is ignored when `TRITON_ALL_BLOCKS_PARALLEL` is not set. |

**逐行解读**

- **Row 1 `multibuffer`**:开启/关闭 ping-pong pipeline,典型多 buffer 流水线并行手段。
- **Row 2 `enable_auto_bind_sub_block`**:仅 CV-fused kernel 生效,控制 sub-block 自动绑定。
- **Row 3 `enable_hivm_auto_cv_balance`**:CV-fused 专用,启用 HIVM 层面的 Cube/Vector 自动负载均衡。
- **Row 4 `sync_solver`**:CV-fused 专用,是否启用同步求解器,用于跨 Cube/Vector 同步依赖。
- **Row 5 `unit_flag`**:开启同步单元标志位,影响硬件同步粒度。
- **Row 6 `inject_barrier_all`**:对所有 OP 自动插入 barrier(屏障),保守地保证顺序。
- **Row 7 `inject_block_all`**:对所有 OP 自动插入 block,影响分块策略。
- **Row 8 `limit_auto_multi_buffer_only_for_local_buffer`**:把自动 multi-buffer 限定在 local buffer 上(可避免对全局 buffer 误用双 buffer)。
- **Row 9 `limit_auto_multi_buffer_of_local_buffer`**:是 Row 8 的细化开关,直接控制 local buffer 的自动多 buffer 行为。
- **Row 10 `set_workspace_multibuffer`**:对 workspace 缓冲区启用/禁用多 buffer。
- **Row 11 `tile_mix_vector_loop`**:CV-fused 专用,是否对 vector loop 做分块。
- **Row 12 `tile_mix_cube_loop`**:CV-fused 专用,是否对 cube loop 做分块。
- **Row 13 `disable_auto_inject_block_sync`**:CV-fused 专用,关闭 block 同步的自动注入。
- **Row 14 `stream`**:可选,显式告知编译器使用哪条 NPU stream,与运行时调度相关。
- **Row 15 `enable_linearize`**:开启/关闭 linearization pass(对应 3.2.2 中 `triton-to-structured` 阶段的 linearize 行为)。
- **Row 16 `enable_nd2nz_on_vector`**:CV-fused 专用,做 ND→NZ 布局变换(ND 即 n 维普通布局,NZ 即 Ascend 硬件常见的非零/分形布局)。
- **Row 17 `auto_blockify_size`**:启用 AutoBlockify pass,**但需 `TRITON_ALL_BLOCKS_PARALLEL` 已设置才生效**,否则被忽略。

> 可以看到,17 个选项里有 7 个标了"CV-fused kernels only"(Row 2/3/4/11/12/13/16),说明 Triton-Ascend 在 Cube(Cube 单元)+Vector(Vector 单元)融合路径上有专门的优化开关,而非通用 kernel 的全局默认行为。

### 表格 3 — 3.2.2 SIMD Compiler(Pass 流水线)

| No. | Pass | Purpose | IR Conversion |
| ------ | ---------------------- | ---------------------------------------------------------------------- | ----------------------- |
| 1 | triton-to-structured | linearize | ttir->ttir |
| 2 | triton-to-unstructured | convert indirect axis to loop | ttir->ttir |
| 3 | triton-to-linalg | memory/reduction/view/creation/math/arith/linear algebra to linalgir | ttir->linalgir |
| 4 | triton-to-other | ttir->hivm/hfusion/llvm | ttir->hfusion/llvm |

**逐行解读**

- **Row 1 `triton-to-structured`**:目的为 linearize(线性化),IR 仍是 `ttir->ttir`,不切换方言,只重排。
- **Row 2 `triton-to-unstructured`**:把间接轴(indirect axis)转换为显式循环,同样是 `ttir->ttir`,为后续按循环展开生成更具体的代码做准备。
- **Row 3 `triton-to-linalg`**:把 memory/reduction/view/creation/math/arith/linear algebra 一系列高阶 OP 下沉到 Linalg 方言,完成 `ttir->linalgir`,这是进入 MLIR 多级 lowering 的关键节点。
- **Row 4 `triton-to-other`**:将 ttir 直接落到 Ascend 后端相关方言 `hivm`、`hfusion`,以及通用的 `llvm`,体现"非 Linalg 路径"的快速通道。

> Pass 顺序隐含的策略是:先在 ttir 内做结构化整理(linearize、间接轴→循环),再大批量下沉到 Linalg,余下的 ttir 直接落到 hivm/hfusion/llvm。

### 表格 4 — 3.2.2.1 TritonToStructured(Converter 矩阵,部分截断)

| Converter | Description | Limitation |
| ------------------------ | -------------------------- | ------------------------- |
| RewriteAddPtrOp | Analyzes the pointer expression (`AddPtrOp`) in operations such as `tl.load` and `tl.store`. The original pointer offset is calculated and modeled into a `PtrState` object that contains the specific offset information of each dimension (axis). For example, for an expression like `ptr + x // 1024 * 4096 + x % 1024 * 4 + y`, the contributions and relationships of the `x` and `y` axes are analyzed. | 1. The original iteration axis (such as `x`) must be exactly divisible by the split axis (such as `1024`).<br>2. The size of the external `XBLOCK` must be an integer multiple or divisor of the split axis `divisor`. |
| CreateAddPtr | Reconstructs a new `AddPtrOp` pointer calculation operation based on the analyzed `PtrState` object to eliminate the integer division (`//`) and modulo (`%`) operations in the original expression. | (原文此处被截断,未给出 Limitation) |

**逐行解读**

- **Row 1 `RewriteAddPtrOp`**:定位是"分析阶段"。把 `tl.load/tl.store` 中 `AddPtrOp` 的指针表达式拆解成各轴的偏移贡献,统一封装到 `PtrState`。原文以 `ptr + x // 1024 * 4096 + x % 1024 * 4 + y` 为例,说明它能拆解 `x` 的"除法+取模"组合与 `y` 的纯线性贡献。
- **Row 1 Limitation**:它对原表达式形式有两条硬性要求——`x` 必须被 `1024` 整除,`XBLOCK` 必须是 `divisor` 的整数倍或因子。这本质上保证编译器能把"x 轴分块"按规则映射到张量维度上。
- **Row 2 `CreateAddPtr`**:定位是"重建阶段"。基于 `PtrState` 重写 `AddPtrOp`,直接消掉 `//` 和 `%`。其 Limitation 在原文截断处未给出,需要查阅后续内容补全。

## 【公式解读】

**原文公式/伪代码(逐字保留):**

```python
Triton IR → Linalg IR → AscendNPU IR → triton_xxx_kernel.o
```

**符号含义与作用**

- `Triton IR`(也叫 `TTIR`):由上层 Triton 编译器生成的中间表示,作为 triton-ascend compiler 的输入。
- `Linalg IR`:MLIR 中的 Linalg 方言,用于结构化表示 memory/reduction/view/creation/math/arith/linear algebra 等操作(对应 3.2.2 Pass 表 Row 3)。
- `AscendNPU IR`:经过 triton-to-other 等 Pass 后落到 Ascend 后端方言(`hivm`、`hfusion`、`llvm`)的中间表示。
- `triton_xxx_kernel.o`:BiSheng Compiler 输出的目标设备可执行二进制 kernel 文件,`xxx` 是占位符(原文逐字形式)。
- 箭头 `→`:表示 IR 之间的转换/降级(lowering),由对应 Pass 完成。

## 【关联】

文档体现的上下游与模块关系如下:

- **上游 — Triton core**:文档明确"target independent 修改保留在 Triton core",且 `compiler` 接收的是"上层 Triton 编译器生成的 TTIR",说明 Triton core 提供语言与 IR 输入。
- **下游 — CANN / BiSheng Compiler**:文档反复提到 `compiler` 通过 BiSheng Compiler 生成 `triton_xxx_kernel.o`,`driver` 借助 CANN 完成 runtime↔设备侧的互连与加载。
- **同层模块耦合**:`include/` 与 `lib/` 提供 MLIR Pass、方言工具 → `backend/compiler.py` 用这些 Pass 完成 lowering → `backend/driver.py` 加载产物。`libdevice.py` 提供硬件相关底层支持,在编译期被 Triton 算子调用。
- **功能模块耦合**:
  - 3.2.1 的 `enable_linearize`(Row 15)对应 3.2.2 Pass 表 Row 1(`triton-to-structured` 的 linearize 目的)。
  - 3.2.1 中 7 个 "CV-fused kernels only" 选项与 3.2.2 的 Pass 流水线共同支撑 Cube/Vector 融合路径。
  - 3.1.1 的三个语言扩展算子(`insert_slice`/`extract_slice`/`get_element`)为 Triton 核心提供与 Ascend NPU 内存视图/切片操作相适配的语义,会被后续 Pass 直接处理。
- **运行环境耦合**:`stream`(Row 14)与 `TRITON_ALL_BLOCKS_PARALLEL`(`auto_blockify_size`,Row 17)把编译期开关和运行期/环境变量绑在一起,体现文档中"编译—运行"协同的设计意图。

  - 硬件抽象支持:`libdevice.py`(提供 `libdevice` API)。

- **代码组织原则**(原文):target independent 改动放在 Triton core;target affinitive 改动放在 Triton-Ascend。
