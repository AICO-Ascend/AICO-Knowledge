# msSanitizer 架构设计说明书 · 一体化深度解读

---

## 【定位】

本文档是 `msSanitizer`（昇腾 AI 处理器专用异常检测工具）的架构总览说明书，定位为解决昇腾片上内存开发中"对齐要求严格、易出现内存踩踏/对齐错误/未初始化访问/流水竞争等难排查问题"的自动化检测工具的整体设计阐述——回答"工具由哪些模块组成、模块如何协作、如何对外提供命令行能力、如何在编译期与运行期两个阶段分别采集数据并产出异常报告"。

---

## 【技术要点】

1. **双阶段采集机制**：通过"**编译器插桩 + 运行时劫持**"两条路径在算子运行期间自动收集行为信息。编译期通过检测插件模块（Plugin）插入静态桩；运行期通过 `LD_PRELOAD` 机制劫持运行时函数符号。
2. **四大模块分层架构**：系统由 `Framework`（框架）、`Runtime`（运行时）、`Processor`（信息处理）、`Plugin`（检测插件）四个核心模块构成，模块间通过 **IPC（DomainSocket）** 与"接口调用"两种方式连接。
3. **检测能力分类（12 项业务功能 + 1 项运行时配置 + 1 项 DFX）**：覆盖非法读写、对齐、多核踩踏、内存泄漏、非法释放、内存未使用、CANN 栈内存、流水间/流水内/核间竞争、未初始化共 11 种异常类型，并提供异常定位信息。
4. **检测算法插件化**：通过 `SanitizerFactory` 创建具体的 `Sanitizer` 实例（见 5.1.2 类图注释），便于后续支持更多异常类型（设计目标"**检测算法易于扩展**"）。
5. **多实例独立运行**：通过 DomainSocket 路径区分（`Process::CreateSockPath()`），保证同一主机多工具实例同时运行互不冲突。
6. **六类核心命令行参数**：`--kernel-name`、`--block-id`、`--cache-size`、`--log-file`、`--log-level`、`--max-debuglog-size`，覆盖"指定 kernel、指定 block、分配 GM 缓存、控制报告输出、调试日志大小"五大维度。

## 【关键机制与数据】

### 工作原理（原文章节映射）

- **整体流程**（§4 核心交互流程 5 步）：用户通过命令行调用 → 工具拉起算子程序并劫持运行时接口 → 编译器在编译阶段插入静态桩（Plugin） → 运行时模块在执行阶段收集行为数据并 IPC 上报 → 信息处理模块分析数据并向用户报告。
- **框架模块处理流程**（§5.1.3 共 6 步）：解析 CLI → 选桩库 → `execvpe` + `LD_PRELOAD` Fork 子进程 → 发送使能模式 → 接收并解析 `SanitizerRecord` → 分发到已启用的 Checker。
- **运行时模块通信流程**（§5.2.4）：首次触发 → socket 连接 → 获取检测模式 → 上报设备信息 →（原文在第 5.2.4 节末尾被截断，仅可读至"根据通信协…"）。

### 异常信息定位的三级粒度（原文 §5.1.4）

- **异常调用栈（最详细）**：含文件名、行号、列号、PC 指针、调用栈帧 `#0 … #3`。
- **文件名与行号（中等）**：仅含 `文件名:行号` 与 PC `serialNo`。
- **无定位信息（最简）**：仅含地址、block、device、`serialNo`。

### 报告原文示例（原文 §5.1.4 示例输出）

```
====== ERROR: illegal read of size 224
======    at 0x12c0c0015000 on GM
======    in block aiv(0) on device 0
======    code in pc current 0x77c (serialNo:10)
======    #0 .../kernel_operator_data_copy_impl.h:58:9
======    #1 .../inner_kernel_operator_data_copy_intf.cppm:58:9
======    #2 .../inner_kernel_operator_data_copy_intf.cppm:443:5
======    #3 illegal_read_and_write/illegal_read_and_write_kernel.cpp:18:5
```

可从该示例直接读出的"原文存在的数据"：`size = 224`、`address = 0x12c0c0015000`、`device = 0`、`block = aiv(0)`、`PC = 0x77c`、`serialNo = 10`、调用栈最多 4 帧。

> 注：上述示例数据来自原文示例文本，为"示例输出"而非性能基准数据；文档**未提供任何性能基准数据**（如检测耗时、吞吐、内存开销等），故此处不另行构造。

### 表 2 · 整体设计目标（§2.1，原文逐字还原）

| 设计目标 | 描述 |
|---------|------|
| **检测准确性** | 将假阴性和假阳性的控制作为关键目标，分别考虑两种情况可能出现的场景 |
| **算子接入方式支持** | 覆盖不同算子接入方式调用的 runtime 接口差异，保证可用性 |
| **检测算法易于扩展** | 检测算法管理采用插件化架构，便于后续支持更多异常类型 |
| **检测耗时** | 尽可能缩短检测耗时，保障大算子、整网检测、多卡检测场景下的可用性 |
| **命令行参数易用性** | 参数设计清晰、直观，保证良好的人机交互体验 |
| **工具多实例运行** | 同一主机上多个工具实例能同时独立运行，互不冲突 |

**逐行解读**：6 项设计目标，构成"质量—覆盖—扩展—性能—易用—隔离"的完整目标体系。其中"**大算子、整网检测、多卡检测**"是文档明确点出的高负载场景，是检测耗时优化的针对性对象。"**插件化架构**"指向 SanitizerFactory 工厂模式。

### 表 3 · 关键要素设计（§2.2，原文逐字还原）

| 关键要素 | 映射的设计目标 |
|---------|-------------|
| **实现模型** | 检测准确性：指令行为抽象和算法实现需保证准确性<br>算法扩展性：算法模块需做合适的抽象<br>算法并行：多卡并行、算法间并行、算法内并行 |
| **交互模型** | 算子接入方式支持：不同接入方式感知不同的内存信息<br>命令行易用性：参数设计清晰直观 |
| **并发模型** | 多实例运行：保证工具间功能独立无冲突 |

**逐行解读**：将表 2 的 6 项设计目标归并为 3 个"实现维度"：**实现模型**承担准确性 + 扩展性 + 三级并行（多卡/算法间/算法内）；**交互模型**承担多接入方式适配 + CLI 易用性；**并发模型**承担多实例隔离。注意"算法内并行"在原文 §5 中并未给出具体实现细节，属设计层面的目标性描述。

### 表 4 · 各模块职责概览（§3.2，原文逐字还原）

| 模块 | 职责 | 关键输入/输出 |
|-----|------|-------------|
| **框架模块** | 流程控制：命令行解析、进程拉起、进程间通信 | 输入：用户命令行参数；输出：检测配置、流程控制 |
| **运行时模块** | 信息采集：劫持运行时接口，收集用户进程行为数据 | 输入：运行时 API 调用；输出：操作信息上报 |
| **信息处理模块** | 异常分析：运行检测算法，生成检测报告 | 输入：运行时信息；输出：异常检测结果 |
| **检测插件模块** | 编译插桩：协同编译器插入检测桩函数 | 输入：插桩策略查询；输出：桩函数实现 |

**逐行解读**：四个模块沿"**入口控制 → 行为采集 → 算法分析 → 编译期插桩**"的完整因果链排列。其中 Runtime 与 Framework 之间是 IPC 双向通道；Framework 向 Processor 单向喂数据；Plugin 是被 Framework/Runtime 调用的"工具提供者"，本身不参与运行时检测。

### 表 5 · 软件单元清单（§3.3，原文逐字还原）

| 软件单元 | 描述 | 外部接口 | 内部接口 | 关系描述 |
|---------|------|---------|---------|---------|
| 框架模块 | 工具整体流程控制 | 工具命令行 | 通信服务端 | 实现命令行供用户调用；实现通信服务端与运行时模块传输数据；使用信息处理模块的信息输入接口 |

| 信息处理模块 | 执行异常检测并输出结果 | 异常输出 | 信息输入接口 | 实现异常输出和信息输入接口，接收框架传入数据 |
| 检测插件模块 | 协同编译器完成插桩 | 插桩查询接口、指令桩实现 | 动态插桩插件 | 实现插桩查询接口供编译器查询；实现指令桩供静态插桩链接；实现动态插桩插件供运行时模块调用 |

**逐行解读**：该表把表 4 的"职责"翻译为"对外接口 vs 对内接口"的契约视角。值得注意的差异：**运行时模块的"外部接口"列为"无"**，意味着运行时模块不直接面向用户，纯靠 `LD_PRELOAD` 隐式注入；**检测插件模块同时拥有"静态插桩"和"动态插桩"两条交付路径**，分别面向编译器和运行时。

| 场景 | 交付件 | 用途 |

> 以下参数全部来自原文 §1.3 功能清单与 §2 关键要素描述的明确表述。

### 命令行参数一览

| 参数 | 来源章节 | 作用 |
|------|---------|------|
| `--kernel-name` | §1.3 业务功能 | 指定要检测的 kernel（运行时参数配置） |
| `--block-id` | §1.3 业务功能 | 指定要检测的 block id（运行时参数配置） |

### 启用流程（原文 §4 核心交互流程）

1. 用户通过工具命令行调用 msSanitizer，传入待检测算子程序；
2. msSanitizer 拉起算子程序并劫持运行时接口（`LD_PRELOAD` + `execvpe`，见 §5.1.3 第 3 步）；
3. 编译器在编译阶段插入静态桩（通过检测插件）；
4. 运行时模块在执行阶段收集行为数据并上报；
5. 信息处理模块分析数据，检测异常并向用户报告。

### 适用场景（原文 §1.2）

- AscendC 单算子场景
- 算子直调、AclNN 单算子调用、PyTorch 接入等常用算子接入方式
- CANN 软件栈的内存检测

系统架构分两栏：**左"检测插桩"**——依托毕昇编译器遍历用户函数，按高阶/泛低阶/计算/同步/内存 API 分层植入检测桩（含语言层组合桩、基础公共桩、桩间/HD/工具通信），DWARF 增强提供行号定位；**右"检测工具"**——含命令解析、应用流程控制、内存/竞争/同步检测算法管理、算法预处理及信息展示模块，通过通信模块与左侧协同。底层落地于昇腾芯片。

**2) 论证的技术结论**
采用"**编译期插桩 + 运行时劫持**"的前后端协同架构，按 API 层级与检测目标**分层模块化**，以通信模块打通编译器侧桩注入与运行时算法分析的信息流，实现对昇腾算子各类异常的精细化、自动化检测。

**3) 与文档论点的关系**
直接印证第 1.1 节"编译器插装与运行时劫持相结合"的核心方案；同时为第 1.3 节功能清单（非法读写、对齐、多核踩踏、流水/核间竞争、未初始化等）提供模块化承载映射，是技术方案的可视化证明。
