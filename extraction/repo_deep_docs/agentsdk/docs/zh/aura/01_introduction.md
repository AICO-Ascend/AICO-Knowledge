# 深度解读：AgentSDK — Aura 简介文档

## 【定位】

本文档作为「Aura 框架」的 overview 文档，定位为**面向通用模型的训推调一体化 Agent 强化学习框架的入门导引**，解决「如何从通用语言模型演化为具备自主规划、工具调用、环境交互能力的行动型智能体」这一核心问题，并给出软件架构全貌与四类受支持训练策略的入口。

---

## 【技术要点】

- **框架命名与定位**：Aura（Agentic Ultra-fast Reinforcement Architecture）以"训、推、调一体化"为核心特征，定位为面向通用模型的后训练（post-training）Agent RL 框架。
- **三要素驱动机制**：以**任务轨迹、环境反馈、奖励信号**作为核心驱动，结合强化学习等后训练技术使模型在与环境持续交互中学习更优策略。
- **统一抽象接口层**：通过统一抽象接口同时兼容多种**训练引擎、推理引擎与 Agent 框架**，并允许接入自定义模型、任务环境、工具链；支持多样化的 RL 算法、奖励机制与优化策略。
- **第三方生态兼容**：明确点名支持的第三方组件为 Agent 引擎侧 **rLLM**、推理引擎侧 **vllm-ascend**、训练引擎侧 **verl**。
- **四类训推拓扑策略**：On-Policy（共卡时分复用）、One Step Off（单步异步分离，训练与推理相差一轮）、Fully Async（全异步分离，相差 0~N 轮）、自定义 Agent 接入，分别对应四份独立 user guide。
- **分布式资源管理**：基于 **Ray** 实现的分布式资源管理，支持**共卡部署**与**分离部署**两种形态。
- **轨道（trajectory）存储抽象**：轨迹数据持久化存储使用 **Episode 格式**，由 Memory 模块承载，由 Rollouter 生成。
- **训练-推理数据流编排**：Trainer 通过 `data_manager` 协调训练侧与推理侧的数据流动；Serve 层负责训练侧→推理侧、训练侧→agent 侧的 **HTTP 通信**；Scheduler 在推理侧提供**负载均衡**。

---

## 【关键机制与数据】

> **原文数据流 / 工作原理梳理**（均依据原文表述，无外推数字）：

- **能力跃迁路径（原文表述）**：

> "通用语言能力 → 自主规划 / 工具调用 / 环境交互 / 任务执行 / 长程决策能力"

这一路径由"任务轨迹 + 环境反馈 + 奖励信号"三要素，通过 RL 等后训练技术持续挖掘实现。

- **模块级数据流（依据表 1 与图 1 整合）**：

  - **Rollouter（轨迹生成）** ← 第三方 Agent 引擎（如 rLLM）  
  - **Rollouter** ↔ **Scheduler（推理请求调度、负载均衡）** ↔ **推理引擎（如 vllm-ascend）**  
  - **Rollouter** → **Memory（Episode 格式持久化）**  
  - **Serve（训推通信，HTTP）** 连接 Train→Inference 侧、Train→Agent 侧  
  - **Trainer** 通过 `data_manager` 协调 Train↔Inference 的数据流，从 Memory / Rollouter 取数据、推送至 **训练引擎（如 verl）**  
  - 整层运行在 **RAY 分布式资源管理**上（支持共卡/分离）

- **训推时序拓扑差异（依据"支持特性"小节原文表述）**：

  - On-Policy：训练与推理**同一组卡**，通过**时分复用**协同运行（严格同步）。
  - One Step Off：训练与推理**不同节点并行**，相差**一轮**的异步训练。
  - Fully Async：在 One Step Off 基础上的完全解耦，训练与推理**相差 0 到 N 轮**。

> 性能数据、训练吞吐、推理延迟等量化指标：**原文未涉及**。

| **Trainer (训练任务编排)** | 训练任务管理和编排，通过 data_manager 协调训练和推理的数据流动                                                                 |
| **推理引擎**             | 支持第三方推理引擎，包括 vllm-ascend                                                                            |
| **训练引擎**             | 支持第三方训练引擎，包括 verl                                                                                   |
| **RAY 分布式资源管理**      | 基于 Ray 的分布式资源管理，支持共卡/分离部署                                                                             |

**逐行解读**：

| 序号 | 模块                              | 角色定位与解读                                                                                                                                                                       |
|------|---------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1    | 第三方 Agent 引擎（如 rLLM）       | 上游"任务侧"入口。负责将外部 Agent 框架（原文明确点名 rLLM）接入到 Aura 的轨迹生成链路中，决定了 Agent 行为的承载形式。                                                                                                            |
| 2    | Serve（训推通信）                  | 跨进程/跨卡边界接口层。明确采用 **HTTP** 作为 Train → Inference 与 Train → Agent 的通信协议，是异步/分离拓扑下训练与推理解耦的物理基础。                                                                                       |
| 3    | Rollouter（轨迹生成）              | 数据生产核心。承担两条关键职责：① 按既定策略采样生成 Agent 轨迹；② 暴露**轨迹管理**与**自定义轨迹生成接口**，是用户接入自定义 agent 的官方扩展点。                                                                                              |
| 4    | Scheduler                       | 推理请求层的"路由器"。负责将 Rollouter 发出的推理请求分配到合适的推理后端，**支持负载均衡**，决定了多 inference worker 场景下的吞吐与延迟表现。                                                                                          |
| 5    | Memory                          | 状态/轨迹落盘层。使用 **Episode 格式**（一段完整的 agent–environment 交互轨迹）做持久化，为 Trainer 与可能的离线评估提供可重放数据源。                                                                                          |
| 6    | Trainer（训练任务编排）              | 训练侧的"指挥中心"。负责训练任务管理与编排，其内部 `data_manager` 子模块专门用于**协调训练与推理之间的数据流动**——即从哪里取数据、何时下发新模型、何时回灌轨迹。                                                                                       |
| 7    | 推理引擎（如 vllm-ascend）          | 原文点名 **vllm-ascend**，表明推理后端针对**昇腾（Ascend）**硬件栈做了适配；这是 Aura 在国产化/异构硬件上的落地点。                                                                                                          |
| 8    | 训练引擎（如 verl）                 | 原文点名 **verl**（Volcano Engine Reinforcement Learning for LLM）。说明原生训练后端基于 verl 框架；其它训练引擎可通过"统一抽象接口"接入。                                                                                  |
| 9    | RAY 分布式资源管理                  | 整个系统的"资源底座"。Ray 同时承担**任务调度**与**资源分配**功能，支持**共卡部署**（On-Policy 语义下训练与推理共享 GPU）与**分离部署**（One Step Off / Fully Async 语义下训练与推理独占节点）两种物理形态。 |

## 图文联合解读

- `Aura框架架构图.png`: 图分三层：顶层为第三方Agent引擎（rLLM/Langchain/xxx），中层为Aura核心（Serve通信、Rollouter轨迹生成、Scheduler调度、Memory持久化、Trainer编排），底层为第三方训推引擎（vllm-ascend、verl等）+Ray分布式调度。数据流：Agent→Serve(HTTP)→Rollouter→Scheduler/Memory，Trainer内infer→data_manager→train循环。

技术结论：Aura以"统一抽象接口+可插拔模块"屏蔽底层异构引擎，通过Serve统一通信、Episode格式统一存储、Scheduler统一调度，实现训推一体化闭环与多引擎兼容。

与文档论点对应：印证"统一训练/推理/优化基础设施""兼容多种引擎""通过轨迹-反馈-奖励驱动RL后训练"三大核心主张，体现"降低工程复杂度"的架构设计意图。
