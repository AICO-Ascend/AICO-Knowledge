# 社区安全设计规范 · 一体化深度解读

## 【定位】
本文是昇腾社区在产品安全领域制定的纲领性**安全设计规范**，目的是在产品设计阶段牵引、指导和约束安全相关决策，以提升社区产品的整体安全质量。

---

## 【技术要点】

1. **个人数据合规框架**：采集需用户同意（敏感数据须单独同意）、遵循最小化原则、加密存储、声明存留期并按时删除；禁止未授权传出客户网络，禁止跨境传输。
2. **接入认证硬性要求**：所有人机/机机管理接口必须有接入认证，禁止存在可绕过认证的"隐秘管理通道"；禁止将口令/私钥等凭据硬编码进发布软件包，凭据须可修改并建议加密存储。
3. **系统运行与发布安全**：遵从操作系统原有安全框架；对外提供远程服务/进程必须用系统低权限账号，禁止使用 `root`；禁止在日志/调测信息中打印口令/密钥；对外发布的软件或独立 AI 软件包必须具备完整性校验机制（数字签名或哈希值校验）。
4. **数据传输安全通道**：实体、节点、网络之间传输机密数据时，须支持通用加密通道或对数据先加密再传输，建议缺省开启；底层协议建议使用 IPSec、MACSec、HTTPS 等业界标准。
5. **密码学算法白/黑名单**：必须使用 ISO、RFC 等权威机构推荐的标准算法与库；明令禁止使用 DES、MD5 等已被破解的算法，禁止使用 RSA 1024 低密钥强度算法，禁止使用 TLS 1.0 等被破解的安全协议（非安全用途可豁免）。
6. **密码学安全随机数**：密码算法所用的随机数必须是密码学意义上的安全随机数，原文给出了三类合规的随机源：`RAND_bytes`（OpenSSL）、`/dev/random`（类 Unix 系统）、`/dev/urandom`（Linux Kernel 5.18 及其之后的版本）。

---

## 【关键机制与数据】

**整体工作原理**：本文档并非实现型文档，而是采用"原则+约束"的方式，按"数据—接入—系统—传输—密码学"五个层次逐层收紧安全要求，形成覆盖全生命周期的安全设计基线。

- **数据层机制**（第 1 章）：以"知情同意 → 最小化采集 → 加密存储 + 访问控制 + 日志审计 → 到期删除 → 边界隔离"构成闭环。注 Z1/Z2 给出"个人数据"与"敏感个人数据"的判定基准，并明确"匿名化"出个人数据范围、"假名化"仍属个人数据，且在中国"未成年人"指未满 14 周岁（原文：未成年人标准在不同国家有不同定义，在中国未满 14 周岁为未成年人）。
- **接入层机制**（第 2 章）：通过"双面强制 + 凭据可改 + 凭据加密"阻断隐蔽通道与凭据泄露。
- **系统层机制**（第 3 章）：通过"低权限账号运行 + 敏感信息不落日志 + 软件完整性校验"降低被攻陷后的爆炸半径，并保证分发链可信。
- **传输层机制**（第 4 章）：要求缺省部署并开启加密通道，使用 IPSec、MACSec、HTTPS 等标准协议（原文）。
- **密码学层机制**（第 5 章）：通过"标准算法白名单 + 弱算法黑名单 + 安全随机数"三件套，把密码学实现风险降到最低。

**关键性能/版本数据**（原文）：
- RSA 密钥强度下限：**≥ RSA 1024 不可用**，即禁止 RSA 1024。
- Linux `/dev/urandom` 须为 **Kernel 5.18 及之后的版本** 才被认定可提供密码学安全随机数。
- 协议黑名单：DES、MD5、TLS 1.0。
- 协议白名单示例：IPSec、MACSec、HTTPS。
- 权威标准来源：ISO、RFC。

## 【使用方法】

原文未涉及具体的启用方式、配置项或命令（本文档是设计规范而非部署手册）。

文档中以"应该 / 须 / 禁止 / 建议"等规范性措辞给出了**约束性条款**（如 1.1、2.1、3.2、5.2），以及以"建议"给出的**推荐性条款**（如 4.1、4.2、2.2 中"建议支持加密存储"）。使用时应：

- 将第 1–5 章条款作为产品安全设计评审的 checklist；
- 涉及算法/协议选型时，优先以第 5.1/5.2 条做白/黑名单核对；
- 涉及随机数生成时，按第 5.3 条采用 `RAND_bytes`（OpenSSL）、`/dev/random` 或 Linux Kernel ≥ 5.18 的 `/dev/random`；
- 涉及跨境或跨客户网络的数据流转时，按第 1.4 条执行前置评估。
