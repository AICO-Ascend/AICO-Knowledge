# MoFix v1.3 — 可靠性演进设计文档 深度解读

---

## 【定位】

这篇文档定义了 MoFix 项目从 v1.2 向 v1.3 演进时，**以"零改动 v1.2 现有代码"为前提**，在新目录 `mofix-v1.3/` 下建立一套"测试体系 + 增量加固"双轨并行的可靠性提升方案，解决 MoFix 在缺乏自动化测试覆盖、外部调用缺乏超时/重试保护、输入校验薄弱、错误响应格式不统一等可靠性短板问题。

---

## 【技术要点】

1. **双方案并行架构（A + C）**：聚焦两个方向——A. 测试体系优先（pytest + mock 全覆盖）与 C. 增量加固（不改架构只加防护层），所有变更隔离在 `F:\7-workspace\mofix-new\mofix-v1.3` 目录内。

2. **测试工具链固定**：pytest 7.x + pytest-asyncio（`asyncio_mode = auto`）+ pytest-cov（初始目标 >60%）+ pytest-mock + ruff；CI 强制 lint。

3. **三级测试分级（P0/P1/P2）**：P0 为离线 CI 必过、P1 为离线 CI 建议过、P2 为可选运行；P0 必过用例总计 41 个，P1 计 61 个，P2 计 47 个。

4. **六大类外部依赖 Mock**：OpenAI/LLM API、subprocess、MCP Server、LTS Logger、File I/O（tmp_path）、Claude Agent SDK，分别采用 `mocker.patch` 不同入口。

5. **四大加固维度（C1–C4）**：C1 外部调用防护（超时常量提取 + 指数退避 3 次重试）、C2 输入校验加强（max_tokens/temperature/c_id 等范围）、C3 结构化日志补全（trace_id 传播链）、C4 错误响应统一（JSON 格式 + not_implemented 结构）。

6. **五阶段实现计划**：Phase 1 基础框架（1 天）→ Phase 2 P0 测试（1 天）→ Phase 3 P1 测试（2 天）→ Phase 4 增量加固（1 天）→ Phase 5 P2 测试与收尾（1 天），共计 6 天工作量。

---

## 【关键机制与数据】

### 工作原理

**测试优先机制**：先建测试基础设施（pytest.ini、conftest.py 全局 fixtures、CI workflow），再补核心模块覆盖；目的是保证"先有回归网，再做加固改动"的安全顺序。

**Mock 解耦机制**：通过 `tests/conftest.py` 集中提供 mock LLM、mock MCP、mock subprocess 等 fixture，使 P0/P1 测试可在离线环境零外部依赖运行；`tests/conftest_local.py` 仅用于本地真实 LLM 调用的可选场景。

**增量加固机制**：C1–C4 全部为"在原文件追加防护逻辑"，不修改调用契约、不重构已有架构——例如为已有 `_invoke_claude_skill_async` 加 `asyncio.wait_for()` 兜底、为 `planner._call_llm` 在降级前先插入重试。

### 关键数据（原文）

- **覆盖率目标**：pytest-cov 初始目标 >60%
- **P0 用例数**：41（8+12+10+3+8）
- **P1 用例数**：61（15+10+12+14+10）
- **P2 用例数**：47（10+6+5+5+8+8+5）
- **CI Python 版本**：3.11
- **重试策略**：`retry_llm_call()` 装饰器，**指数退避 3 次**
- **既有超时散落值**：600s、1800s（doc_tools）
- **新加固默认超时**：300s（asyncio.wait_for 兜底）
- **max_tokens 范围**：[1, 131072]
- **temperature 范围**：[0, 2]
- **c_id 最大长度**：128
- **时间戳校验**：非未来 >1h
- **CI 触发条件**：integration-test 仅在 `push && refs/heads/main` 时运行
- **CI 执行命令**：`pytest tests/ -m "not slow and not integration" --cov=app --cov-report=term-missing`

## 【表格解读】

### 表 1：框架与工具

| 工具 | 用途 |
|------|------|
| `pytest` 7.x | 测试框架 |
| `pytest-asyncio` | 异步测试支持，`asyncio_mode = auto` |
| `pytest-cov` | 覆盖率报告，目标初始 >60% |
| `pytest-mock` | 外部依赖 mock |
| `ruff` | lint 检查（CI 中运行） |

**逐行解读**：固定使用 Python 生态最成熟的测试组合，pytest-asyncio 的 `auto` 模式省去逐个测试加 `@pytest.mark.asyncio`，pytest-cov 提供覆盖率门槛（>60% 为起点），pytest-mock 是 mocker 命名空间的来源，ruff 替代 flake8/black 提供极速 lint。注意：pytest 主版本明确锁在 7.x。

---

### 表 2：Mock 策略

| 外部依赖 | Mock 方式 | 适用模块 |
|----------|----------|---------|
| OpenAI/LLM API | `mocker.patch('langchain_openai.ChatOpenAI.invoke')` | agent_engine, chat_service, workflow/planner |
| subprocess | `mocker.patch('subprocess.run')` | doc_tools, claude_tools |
| MCP Server | mock `MCPToolManager` 类 | workflow/executor |
| LTS Logger | `mocker.patch('lts_logger.log')` | 全局 |
| File I/O | `tmp_path` fixture | doc_tools, search_tools, experience |
| Claude Agent SDK | `mocker.patch('claude_agent_sdk.query')` | claude_tools |

**逐行解读**：Mock 分两类——`mocker.patch` 用于拦截具体函数/方法调用，`tmp_path` fixture（pytest 内置）用于隔离文件系统读写。LLM API 的 mock 锚定在 LangChain 的 `ChatOpenAI.invoke`（而非 OpenAI SDK 底层），说明 MoFix 上层统一走 LangChain 抽象；MCP Server 通过替换类对象而非具体方法，体现 executor 与 MCP 是依赖倒置关系。

### 表 6：C1 外部调用防护

| 位置 | 问题 | 加固措施 |
|------|------|---------|
| `app/tools/doc_tools.py` | 超时值散落（600s, 1800s） | 提取为模块常量 `_SUBPROCESS_TIMEOUT`、`_ONE_CLICK_TIMEOUT` |
| `app/tools/claude_tools.py` | `_invoke_claude_skill_async` 无整体超时 | 增加 `asyncio.wait_for()` 兜底（默认 300s） |
| `app/tools/workflow/mcp_integration.py:415` | `_discover_tools` 缺超时 | 给 `send_and_receive` 增加 timeout 参数 |
| `app/core/llm_factory.py` | LLM 调用无重试 | 新增 `retry_llm_call()` 装饰器（指数退避 3 次） |
| `app/tools/workflow/planner.py:448` | `_call_llm` 失败后仅降级 | 先重试再降级 |

**逐行解读**：C1 解决"调用外部世界时缺乏时间边界和失败容忍"的问题。三处补超时（subprocess 常量化、claude async 兜底、mcp send_and_receive 参数化）+ 一处补重试（LLM 通用装饰器）+ 一处改造既有降级路径（planner 由"直接降级"升级为"先重试再降级"）。

### 表 7：C2 输入校验加强

| 模型/位置 | 加固内容 |
|-----------|---------|
| `ChatCompletionRequest.max_tokens` | 范围 [1, 131072] |
| `ChatCompletionRequest.temperature` | 范围 [0, 2] |
| `ChatCompletionRequest.c_id` | 最大长度 128 |
| `ChatMessage.content` | 空字符串转为 None 的统一处理 |
| `ChatCompletionChunk.created` | 验证时间戳合理性（非未来 >1h） |

**逐行解读**：C2 围绕 Pydantic 模型加边界。`max_tokens` 上限 131072 对齐 OpenAI GPT-4 级别上下文窗口；`temperature` 上限 2 同样对齐 OpenAI API 规范；`c_id` 限制 128 字符防止会话标识被滥用；`created` 时间戳反未来校验可识别时钟漂移或伪造响应。

### 表 8：C3 结构化日志补全

| 位置 | 补充日志 |
|------|---------|
| `app/core/agent_engine.py` | build_agent 成功/失败、tools 加载数量 |

**逐行解读**：C3 构建端到端可观测性。trace_id 从 API 入口（`app/api/chat.py:16`）注入，经 chat_service 传到 workflow，最终在 planner/executor 形成完整链路。token 消耗日志为成本审计提供数据点。

### 表 9：C4 错误响应统一

| 位置 | 当前行为 | 加固后 |
|------|---------|--------|
| `chat_service.py` 命令执行失败 | `f"[错误] 执行失败：{e}"` | 统一 JSON 错误格式 |
| `handle_api_error` | 抛出异常 | 确保所有 LLM 调用点在外层 try/except |
| 骨架工具返回值 | 占位字符串 | 调整为 `{"status": "not_implemented", "message": "..."}` 格式 |

**逐行解读**：C4 把"散落的字符串错误"收敛为"结构化响应"。`not_implemented` 状态字段让前端可识别骨架工具与真错误，避免误把"功能未实现"当成"执行失败"展示给用户。

## 【关联】

由于文末提供的内部链接信息为"无"，以下关联完全基于文档正文内容梳理：

- **与 v1.2 的关系**：v1.3 是基于 v1.2 的增量演进，所有 `app/`、`commands/`、`skills/`、`agents/` 从 v1.2 **原样复制不做代码改动**（加固除外），属于严格的"上一代继承 + 旁路加固"模式。
- **与测试基础设施的关系**：v1.3 是 v1.2 第一次系统性引入 pytest 体系，`tests/` 目录为全新构建，与既有 `app/` 形成被测/测试对应关系（tests/core ↔ app/core，tests/services ↔ app/services，tests/workflow ↔ app/tools/workflow，tests/hermes ↔ app/hermes）。
- **与 Hermes 模块的关系**：`tests/hermes/` 表明 Hermes 在代码仓内是独立子模块，拥有自己的 store 与 memory 组件，被 v1.3 单独纳入 P2 测试范围。
- **与 LangChain/OpenAI 生态的关系**：mock 锚点 `langchain_openai.ChatOpenAI.invoke` 揭示上层 LLM 抽象走 LangChain，而非直接调 OpenAI SDK；这意味着任何 LangChain 版本升级都直接影响 v1.3 的 LLM 工厂可靠性。
- **与外部依赖（Dify、Claude Agent SDK、MCP Server）的关系**：通过 mock 策略显式声明三类外部依赖边界——Dify 在 search_tools 中可选导入失败降级、Claude Agent SDK 通过 `claude_agent_sdk.query` 被替换、MCP Server 通过 `MCPToolManager` 类被替换。
- **与 CI/CD 基础设施的关系**：`.github/workflows/ci.yml` 是 v1.3 新增的 GitHub Actions 配置，三 job（lint / unit-test / integration-test）形成质量门禁；integration-test 受保护（仅 main 分支 push 触发），避免外部 API 配额消耗。
- **与本仓"model-agent"主项目的隐含关系**：路径 `docs/superpowers/specs/2026-06-11-mofix-v1.3-reliability-design.md` 表明这是 superpowers 知识体系下的规格说明（spec），被主仓的 model-agent 系统作为可执行规范引用。

## 【使用方法】

启用方式与命令（原文涉及部分）：

**本地安装测试依赖**：
```bash
pip install pytest pytest-asyncio pytest-cov pytest-mock
pip install ruff
```

**本地运行单元测试（离线，排除 slow 和 integration）**：
```bash
pytest tests/ -m "not slow and not integration" --cov=app --cov-report=term-missing
```

**本地运行集成测试（需真实 OPENAI_API_KEY）**：
```bash
pytest tests/ -m integration
```
需先设置环境变量 `OPENAI_API_KEY=${{ secrets.OPENAI_API_KEY }}`。

**本地 lint 检查**：
```bash
ruff check app/ tests/
```

**CI 自动触发条件**：
- `push` 与 `pull_request`：触发 `lint` 与 `unit-test` 两个 job
- 仅 `push && refs/heads/main` 时：额外触发 `integration-test` job

**配置项（pytest.ini 与 requirements-dev.txt，原文未给出具体内容模板）**：
- `asyncio_mode = auto`（pytest-asyncio 配置项）
- 初始覆盖率门槛 >60%（pytest-cov 配置项）
- requirements-dev.txt 须包含：pytest、pytest-asyncio、pytest-cov、pytest-mock、ruff

**全局 fixtures 调用**（在 `tests/conftest.py` 中定义）：
- mock LLM
- mock MCP
- mock subprocess
- 另在 `tests/conftest_local.py` 提供"本地专用 fixtures（真实 LLM 调用）"，仅供本地手动调试使用，不进入 CI。

**原文未涉及**：具体的 pytest.ini 完整配置模板、requirements-dev.txt 的版本钉死方式、conftest.py 的 fixture 签名定义、CI 各 job 间的依赖关系、覆盖率未达标时的失败阈值（`--cov-fail-under` 是否启用未说明）。
