# 一体化深度解读：test-design-template.md

## 【定位】

本文档是 AscendC 算子白盒测试设计流程中的**标准化产出模板**，用于在源码分析（tiling/kernel/param_def）完成后，自动生成结构化的 `test_design.md` 测试设计方案，覆盖「输入概览 → 路径全景 → 派生变量 → 测试 group → 执行模式 → 未确认项 → 验证结论」的完整设计链条，最终供下游 pytest 用例生成引擎消费。

---

## 【技术要点】

1. **四类输入溯源**：模板要求明确标注 torch 接口、tiling 代码、kernel 代码、资料描述四类输入是否提供，每条事实摘要必须打上「来源类别」和「类型」标签，保证可追溯性。
2. **分支树全景建模**：第 3 节要求产出从 tiling 入口到 kernel 叶子节点的完整分支树，并统计 `N` 条路径、`M` 个 group，作为测试覆盖的基础骨架。
3. **三层执行覆盖策略**：第 6 节显式建模 分核 / UB 切分 / 指令对齐 三层，每层对应明确的触发条件（如 `dim < coreNum` 触发「未开满核」、`dim % vectorWidth == 0` 触发「指令对齐」）。
4. **9 维 data_range 标签体系**：提供 normal / zero / extreme / negative / tiny_pos / all_ones / near_zero / with_inf / with_nan 九种语义标签，每种对应具体的数值构造方式和测试目标（如 `extreme` 测溢出饱和，`with_nan` 测 nan 传播）。
5. **desc_rules 自动描述引擎**：以 JSON 数组定义 `formula`/`if` 规则，引擎据此为每个参数组合自动拼接 `_desc` 描述（如 `"未开满核; 指令非对齐"`），多规则用 "; " 拼接。
6. **未确认项强制用户决策**：第 7 节要求将无法从输入中确认的所有问题列表化（带原因和建议处理），并在 Step 2 后停顿等用户逐条确认，体现「人在回路」的设计哲学。

---

## 【关键机制与数据】

**工作流程**（原文模板结构）：
- 输入：`param_def.json`（参数推导结果）+ `low_configs`（常见网络 shape）+ 用户确认结果
- 产出：符合模板的 `test_design.md`
- 流程节点：Step 2 完成后展示未确认项 → 等用户确认 → Step 3 由 verifier 填写验证结论

**group 自包含要求**（原文 5.N 节）：每个 group 必须自包含四要素——**路由条件 + 约束 + 维度表 + 预估组合数**。

**分组数与路径数关系**：原文明确以 `{N}` 条路径、`{M}` 个 group 作为可量化指标，由 Agent A 产出。

**ndim 维度的条件性**：原文明确「如果算子固定 ndim（如必须 4D），不加此维度」，说明 ndim 是按算子语义可选引入的维度。

### 表 10：data_range 标签语义

| 标签 | 含义 | 测什么 |
|------|------|--------|
| normal | torch.randn 正态随机 | 一般场景 |
| zero | 全零 | 零值传播、除零保护 |
| extreme | 接近 dtype 最大值 | 溢出、饱和 |
| negative | 全负数 | sigmoid/silu 负值分支 |
| tiny_pos | 极小正数（~1e-6） | 精度损失、scale 除零 |
| all_ones | 全 1 | 恒等验证 |
| near_zero | 接近零的正负混合 | 符号翻转、舍入 |
| with_inf | 正常数据中混入 inf | inf 传播处理 |
| with_nan | 正常数据中混入 nan | nan 传播处理 |

**逐行解读**：9 个标签构成完整的数值边界测试矩阵。需特别关注：**量化算子至少需要 normal/zero/extreme/negative**（原文硬性要求）；`with_inf`/`with_nan` 通常仅在涉及 log/div/sqrt 等易产生特殊值的算子中使用；`tiny_pos`（~1e-6）和 `near_zero` 都涉及零值附近但语义不同——前者强调「极小正数下的精度退化」，后者强调「跨零点的符号翻转与舍入边界」。

## 【公式解读】

**原文无独立公式章节**，但模板内嵌了三类隐含公式（以参数化形式表达）：

1. **`CeilDiv(dim, coreNum)`** —— 分核轴控制变量
   - `dim`：待切分维度大小
   - `coreNum`：AI Core 数量
   - `CeilDiv`：向上取整除法，结果即为每个核承担的数据块大小

2. **`UbFactor 公式`** —— UB 切分轴控制变量
   - `UbFactor`：由 `总 UB 容量 / 单元素字节 / 向量化系数` 推导出的单核单次可处理元素数
   - 原文以占位符 `{UbFactor 公式}` 呈现，由具体算子填充

3. **`{k*v-1 展开值}`** —— 指令非对齐时的维度取值模式
   - `v`：即 `vectorWidth`（向量化宽度，如 32、64）
   - `k`：倍数系数
   - `k*v - 1`：构造「减去一个向量宽度后必非整除」的边界值，用于触发非对齐代码路径

4. **`desc_rules` 中的 formula 模式**（原文示例）：
   - `"inDimx < 64"` → desc: `"未开满核"`
   - `"inDimx == 64"` → desc: `"开满核无尾核"`
   - `"x_last % 32 == 0"` → desc: `"指令对齐"`
   - `"x_last % 32 != 0"` → desc: `"指令非对齐"`
   
   这些 formula 由 desc_rules 引擎求值，多条匹配结果以 "; " 拼接成完整 `_desc`。

## 【关联】

本文档处于 AscendC 白盒测试设计流水线的**核心产出位置**，上下游关系如下：

- **上游输入**：
  - 参数推导结果 `param_def.json` —— 提供第 2、4 节的事实与变量定义
  - 常见网络 shape `low_configs` —— 提供低频测试配置（其 `note` 字段会自动作为 `_desc`）
  - Agent A 产出 —— 提供第 3 节的代码路径全景（{N} 路径 / {M} groups）
  - 用户确认结果 —— 关闭第 7 节的未确认项

- **下游消费**：
  - pytest 用例生成引擎 —— 根据 `desc_rules` 自动拼接 `_desc`，根据维度表生成参数化测试用例
  - 第 9 节「验证结论」由 verifier 在 Step 3 完成后回填，闭环设计质量

- **同级关联**：
  - 与同目录其他模板（如 param-derivation、code-analysis 模板）共同构成完整的白盒设计 prompt 套件
  - `data_range` / `ndim` / `desc_rules` 是与 pytest 生成引擎**强契约**的字段，命名不可变更

- **强约束关系**：
  - 量化算子与 `data_range` 标签存在硬性最小集约束（normal/zero/extreme/negative 至少包含）
  - 三层覆盖策略表（第 6 节）是 group 维度表（第 5 节）`轴角色` 列的**穷举基准**

## 【使用方法】

**启用流程**（原文模板「用途」节）：

1. **触发时机**：源码分析完成后启动 Step 2。
2. **输入装配**：将 `param_def.json`、`low_configs`、用户确认结果作为输入填充模板。
3. **填写必填章节**：依次完成第 1～8 节（输入概览 → 事实摘要 → 路径全景 → 派生变量 → 测试 group → 执行模式 → 未确认项 → 设计估算）。
4. **同步点**：Step 2 完成后必须将「未确认项表」展示给用户，逐条确认或补充后再进入 Step 3。
5. **验证闭环**：Step 3 由 verifier 填写第 9 节「验证结论」。

**关键配置项**：

| 字段 | 是否必须 | 说明 |
|------|---------|------|
| `data_range` | 是（除非算子特殊限制） | 9 个标签中按算子语义选择 |
| `ndim` | 条件性 | 仅当算子支持多 rank（2~8）时加入 |
| `desc_rules` | 是 | 每 group 必备，驱动自动描述生成 |
| `轴角色` | 是 | 必须从 `core_split / ub_tile / instruction_align / attr` 四选一 |

**量化算子专项要求**（原文）：`data_range` 至少包含 `normal` / `zero` / `extreme` / `negative` 四个标签。

**desc_rules 多规则拼接规则**（原文）：多条规则匹配时，描述以 "; "（分号空格）连接。`low_configs` 的 `note` 字段会**自动**作为 `_desc` 注入。

> **注**：本文档为「模板」，所有 `{op_name}`、`{N}`、`{M}`、`{dim_name}`、`{source:line}` 等占位符均由 Agent 在填充时替换为实际算子信息。模板本身不绑定具体命令或参数。
