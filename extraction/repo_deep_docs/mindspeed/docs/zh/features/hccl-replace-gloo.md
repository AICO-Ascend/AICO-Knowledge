# Gloo存档落盘优化 一体化深度解读

## 【定位】

这篇文档面向**大规模集群(昇腾/Ascend)下使用 MindSpeed 框架进行分布式训练**的场景,针对 **Gloo 通信在大规模集群下的规模限制与稳定性问题**(典型报错 `Gloo connectFullMesh failed with ...`),给出两路对策:**网络参数调优(规避)** 与 **HCCL 通信组替换 Gloo 通信组(根治)**,并以切片(`hccl-slice-size`)机制控制单次通信数据量,在通信效率与显存占用之间取得平衡,从而提升分布式优化器状态保存/加载环节的稳定性与效率。

---

## 【技术要点】

1. **典型报错特征**: `Gloo connectFullMesh failed with ...`,根因是 N 张卡集中连主节点建链,主节点处理能力不足导致建链失败(8k 卡规模场景验证)。
2. **网络层规避参数(原文给出,云上 8k 卡场景验证有效)**:
   ```text
   net.ipv4.tcp_max_syn_backlog = 65536
   net.core.netdev_max_backlog = 65536
   ```
3. **核心替代机制**: 用 **HCCL 通信组** 替换 **Gloo 通信组**,实现原有功能基础上的替代(原生通信后端由 Gloo → HCCL)。
4. **切片机制**: 将单次通信的大块数据切成较小切片,减少单次通信的数据量,避免通信量过大导致的显存消耗。
5. **启用开关**: 训练脚本添加 `--disable-gloo-group`。
6. **可选切片参数**: `--hccl-slice-size N`,有效区间 `(0, bucket_size/dp]`,其中 `bucket_size` 为分布式优化器每个桶的大小;建议在显存允许情况下尽量增大该参数以提高通信效率。
7. **显存增量代价**: 开启特性后显存增量为 `hccl-slide-size * (2 * dp + 1) * 4Byte`。

---

## 【关键机制与数据】

### 工作原理
- **替换路径**: 将原本由 Gloo 承担的 **分布式优化器状态保存/加载** 通信链路,改由 **HCCL 通信组** 完成。HCCL 是昇腾亲和的集合通信库,在大规模集群下的连通性与吞吐均优于 Gloo。
- **切片控制数据量**: 通过 `hccl-slice-size` 把一次大块集合通信拆成若干小切片,既缓解单次通信的显存压力,又使得大块数据可流水化处理。
- **双路策略**: 文档同时给出 **网络参数调优**(临时规避)与 **HCCL 替换**(根本解决)两套手段,前者无需改代码即可缓解建链失败,后者需打开 `--disable-gloo-group`。

### 性能数据
> 原文备注的参考数据位于被 `<!-- -->` 包裹的注释块中,源码存在但未在前端渲染,此处如实转录:

| 切片大小 | 模型保存效率 | 模型加载效率 |
|---|---|---|
| `10 * 1024 * 1024`(≈10 MiB) | 与原来相当 | 加载时间**有所增加** |
| `30 * 1024 * 1024`(≈30 MiB) | 与原来相当 | 与原来相当 |
| `100 * 1024 * 1024`(≈100 MiB) | **有所提升** | **有所提升** |

> 原文(注释内):「理论上,分布式优化器状态保存和加载的通信效率在一定范围内随着 `hccl-slice-size` 增加而提升」。

> 原文:网络参数 `tcp_max_syn_backlog = 65536`、`netdev_max_backlog = 65536` 在 **云上 8k 卡场景** 验证可规避 Gloo 建链失败。

## 【公式解读】

### 公式 ① 显存增量公式(原文)

$$
\Delta_{\text{mem}} \;=\; \text{hccl-slice-size} \times (2 \cdot dp + 1) \times 4 \text{Byte}
$$

**符号含义与作用**(均为原文出现或可由原文直接推出):

| 符号 | 含义 | 作用 |
|---|---|---|
| `hccl-slice-size` | 切片大小(单位:Byte) | 决定单次切片通信的缓冲大小,是显存占用的线性放大因子 |
| `dp` | 数据并行度 (data-parallel size) | DP 组规模,决定需要缓存的并行副本/通信缓冲数量 |
| `2 * dp + 1` | 与 DP 规模相关的副本/缓冲系数 | 与 DP 组保存/加载分布式优化器状态的 buffer 数量成正比;`+1` 通常对应一份主缓冲或冗余缓冲 |
| `4 Byte` | 单元素字节数 | 对应 `float32` 单精度浮点,与分布式优化器状态以 FP32 存储的常见假设一致 |

> **作用**:给出开启 `--disable-gloo-group` 特性后 **显存峰值增量** 的快速估算式,用于在设置 `--hccl-slice-size` 前评估显存预算。

### 公式 ② 切片大小有效区间(原文)

$$
\text{hccl-slice-size} \in \left(0,\; \dfrac{\text{bucket\_size}}{dp}\right]
$$

**符号含义与作用**:

| 符号 | 含义 | 作用 |
|---|---|---|
| `hccl-slice-size` | 切片大小 | 通信粒度的可控变量 |
| `bucket_size` | 分布式优化器中每个桶的大小 | 来自分布式优化器(分布式 Optimizer State)的内部参数,代表一次桶同步的总字节数 |
| `dp` | 数据并行度 | 分母,表示该桶的数据被均分到 `dp` 个 rank 上 |
| `bucket_size / dp` | 单 DP rank 上每桶的均摊字节数 | 切片粒度的理论上限:切片再大,单 DP 上每桶已被切尽,继续放大无实际收益 |

> **作用**:界定 `--hccl-slice-size` 的合法配置范围;在显存允许时,贴近上界取值可获得更优通信效率(通信次数更少)。

## 【关联】

- **上游问题域**: 大规模分布式训练中 Gloo 通信库的 **规模性瓶颈**(主节点建链成为单点)与 **效率瓶颈**(集合通信吞吐低于 HCCL)。
- **替代关系**: 本特性是 **HCCL ↔ Gloo** 的替代型优化,建立在 MindSpeed 已集成 HCCL 通信库的基础上,涉及集合通信后端选型。
- **与分布式优化器的耦合**: `--hccl-slice-size` 的合法上界依赖 **分布式优化器桶大小**(`bucket_size`)与 **数据并行度**(`dp`),即与分布式优化器状态保存/加载模块直接联动。
- **与方法论的协同**: 文档同时给出 **OS 网络层参数调优**(`tcp_max_syn_backlog`、`netdev_max_backlog`)作为轻量级规避手段,与本特性的 **HCCL 替换方案** 形成"先调参、再替换"的二段式处置路径;前者不改业务代码,后者需要脚本开关。
- **显存与通信效率的权衡**: 通过公式 ① 与公式 ② 联合,可对 `hccl-slice-size` 做显存-效率的帕累托选型。

## 【使用方法】

> 以下均来自原文,逐条复述。

1. **启用特性(必选)**:在训练脚本中加入 `--disable-gloo-group`,以启用该特性。
2. **设置切片大小(可选)**:在脚本中定义 `--hccl-slice-size N`,设置 DP 组保存和加载分布式优化器状态时的通信量大小。
   - **有效区间**: `(0, bucket_size/dp]`,其中 `bucket_size` 为分布式优化器中每个桶的大小。
   - **调优建议**:在显存允许的情况下,尽量增大该参数,以提高通信效率。
3. **辅助规避手段(可选,与特性正交)**:调整网络参数 `net.ipv4.tcp_max_syn_backlog = 65536` 与 `net.core.netdev_max_backlog = 65536`,云上 8k 卡场景下可规避 Gloo 建链失败。
