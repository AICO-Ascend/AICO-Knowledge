# 「PP支持动态形状」feature 文档深度解读

---

## 【定位】

这篇文档描述了在采用流水线并行（PP, Pipeline Parallelism）策略训练大模型时，**如何使各微批次保留原始序列长度（而非统一填充/截断）**，通过在张量传输前预先同步形状信息，解决变长序列在 PP 场景下因强制填充带来的内存与计算资源浪费问题。

---

## 【技术要点】

核心机制分条如下：

1. **问题域**：在多模态训练或变长文本任务中，原本 PP 策略需要把同一 batch 内的所有序列 padding/truncate 到同一长度，造成大量无效 token 占据显存与算力。
2. **核心机制**：在**发送张量之前**，把张量的形状信息提前通信出去，使**各 PP stage 同步"即将接收"的数据形状**，从而按真实形状做内存分配与预处理，避免依赖统一长度假设。
3. **触发前提**：必须启用流水线并行，即 `--pipeline-model-parallel-size ${PP}` 且 `${PP} >= 2`；同时需打开 `--variable-seq-lengths` 开关。
4. **已知限制 / 不兼容项**：暂**不支持**两种 MoE token 调度模式：`--moe-token-dispatcher-type alltoall_seq` 与 `--moe-token-dispatcher-type allgather`。
5. **使用禁忌**：当 PP 策略下序列长度本就**固定**时，开启该特性会引入额外通信开销，原文明确**不建议使用**。
6. **运行时风险**：需监控训练过程中内存消耗，**避免因序列长度波动触发显存溢出**。

---

## 【关键机制与数据】

**工作原理（原文核心描述）**：

> 原文："此功能通过在发送张量之前，提前通信张量的形状信息，在各个流水线阶段之间同步即将接收的数据形状，确保内存分配和预处理的准确性。"

拆解为三步：
1. **形状预通信**：在 PP stage 间的张量传递管道中，先于 payload 发送 shape descriptor。
2. **形状同步**：各 stage 据此知道下一段要接收张量的真实维度。
3. **按真实形状分配/预处理**：接收端据此为即将到达的张量分配显存、做必要的预处理（如重塑、索引），省去把变长序列硬填到统一长度的步骤。

**数据流层面的影响**：
- 输入侧：每个 micro-batch 内部各样本可保留各自原始序列长度，不再要求 batch 内等长。
- 通信侧：在 PP stage 边界增加一次额外的 shape 同步通信（这就是固定长度场景下被警告的开销来源）。
- 计算/内存侧：去除 padding token 带来的无效算力与显存占用。

## 【使用方法】

**启用步骤（原文给出）**：

```bash
# 开启流水线并行，PP >= 2
--pipeline-model-parallel-size ${PP}

# 开启 PP 支持动态形状
--variable-seq-lengths
```

**前置条件**：
- 必须满足 `${PP} >= 2`（即至少两级流水线）。

**注意事项（原文 NOTE 原话）**：
- 当采用流水线并行策略**且序列长度固定**时，启用该特性将增加不必要的通信开销，**不建议使用**。
- 需密切监控训练过程中的**内存消耗**，避免因序列长度变动引起的**溢出**问题。
- **暂不支持** `--moe-token-dispatcher-type alltoall_seq` 与 `--moe-token-dispatcher-type allgather`。

**典型适用场景**（原文所列）：
- 文档分类、机器翻译等文本长度差异显著的任务。
- 期望提升模型对各种长度输入的泛化能力时。

**典型不适用场景**（原文所列/暗示）：
- PP 下序列本就等长。
- PP 下序列需被截断以保持一致长度。
- 使用上述两种被排除的 MoE dispatcher 类型时。

**调优建议（原文"使用效果"部分给出的定性提示）**：
- 启用前应评估"序列长度变动幅度"与"通信开销增加"之间的取舍。
- 应同时设计内存监控策略以应对 length 波动导致的峰值显存变化。
