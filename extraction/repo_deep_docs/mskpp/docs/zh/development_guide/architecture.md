# mskpp 架构设计说明书 深度解读

## 【定位】

本篇文档系统阐述 **msKPP（MindStudio Kernel Performance Prediction）** 的整体架构设计：作为一款**性能仿真工具**，它面向昇腾芯片场景，支持用户通过 DSL 输入算子表达式，在不执行真实计算的前提下，依据输入/输出规模与算法实现，秒级预测算子性能上限；相较 cycle 级仿真器获得数量级速度提升，同时覆盖性能建模与自动寻优两条业务链路。

---

## 【技术要点】

1. **预测机制的本质简化**：msKPP 不进行真实计算，而是依据"输入/输出规模"与算法逻辑给出执行时间，故结果为性能上限（performance upper bound），且仿真速度相对 cycle 级仿真器提升"数量级"，输出可在"秒级"完成。
2. **双轨功能架构**：分为「建模（2.1）」与「自动寻优（2.2）」两大业务模块；建模侧覆盖搬运通路、随路转换、Cache 命中率、tensor 拆分、pipe 理论值与 msprof 实测比对、指令信息统计、指令流水图、指令占比饼图等 8 类业务能力 + debug 模式与性能数据补充 2 类 DFX 能力；自动寻优侧则提供模板库算子下发 C++ 代码自动生成、内置/自定义编译选项编译、kernel 性能度量、跨工具协同、kv 格式参数自动替换与 msopgen 工程轻量化调度。
3. **设计三目标**：① 代码易扩展——针对昇腾"基础指令上百种"提供易用指令注册；② 数据一致性——保障搬运类与计算类指令在不同流水上耗时计算统一，扩展时数据流归一；③ 调度低延时——DSL 建模过程需计算大量指令，需考虑跨语言调用更快速地调度算法。
4. **关键要素-模型映射**：实现模型 → 代码易扩展；交互模型 → 数据一致性；并发模型 → 查询高并发（即调度低延时的实现层映射）。
5. **核心五模块逻辑视图**：INSTR_TASK（指令任务创建）→ INSTR_SCHEDULE（指令调度）接收 PROF_DATA（指令性能数据） → 调度结束后生成 TRACE（指令流水图）与 METRICS（指令性能数据），构成"输入→调度→产出"三阶段闭环。
6. **INSTR_TASK 静态结构**：指令任务由 `ComputationInstruction`（计算指令）与 `MemoryInstruction`（搬运指令）构成，二者均继承 `InstructionBase` 并最终聚合为 `InstrTask`（实现 `RawTask` 接口）；计算指令采用**工厂模式（RegisterOf + Apis）** 注册，支持 `Mmadd`、`vxx` 等具体指令以 `infer_shape` 推导输入输出元组。
7. **PROF_DATA 静态结构**：通过 `PrefModel` 接口暴露 `size()` / `time()`，由 `MmadPref`、`MovPref`、`VxxPref(vector_instructions)` 等子类实现；C++ 侧 `Instructions_Data`（含 `MmadData`、`MovData`、`VxxData(vector_instructions)`）作为底层数据源被 `Instructions_Profiling_Data` 引用，二者通过 `RegisterOf` 完成注册解耦。

---

## 【关键机制与数据】

**性能建模三阶段（原文 §4.1.1.1）：**
1. **指令集拆解**：将 DSL 拆解为统一的指令集和调度任务（对应 INSTR_TASK 模块）。
2. **指令调度**：模拟芯片行为对输入指令进行统一调度，得到不同指令的调度耗时和起止时间（对应 INSTR_SCHEDULE 模块）。
3. **数据解析**：根据指令调度结果生成不同维度的指令分析数据（指令耗时统计、指令流水等，对应 TRACE / METRICS 模块）。

**模块调用关系（原文 §4.1.1.3）：**
- `instr_task → instr_schedule`（Usage）
- `prof_data → instr_schedule`（Usage）
- `instr_schedule → trace`（Realization）
- `instr_schedule → metrics`（Realization）
- `instr_task → a`（realization，外部用户通过接口 a 调用）

**指令生命周期关键方法（原文 INSTR_TASK 静态结构图）：**
`launch(inputs, outputs)` → `is_ready()` → `cost_time()` → `schedule_post()`，覆盖指令发射、就绪判定、耗时计算、调度后置处理完整链路。

**性能对比维度（原文 §2.1 表）：** 支持"pipe 信息的理论值与 msprof 实测值比对"，将建模数据与实测值比较，作为模型校准闭环。

> 注：原文未给出具体吞吐量、命中率百分比或耗时数字等性能数据；仅说明"数量级"提速与"秒级"出结果。

### 表 3：§3.2 关键要素设计

| 关键要素 | 设计目标 |
|---|---|
| 实现模型 | 代码易扩展：算子在不同芯片平台建模依赖大量基础指令，指令调度时需要支持对不同指令数据的自主注册。 |
| 交互模型 | 数据一致性：算子性能建模依赖对不同指令在不同流水上耗时计算，需要有机制保障搬运类和计算类不同指令一致计算，指令扩展时保障数据流归一。 |
| 并发模型 | 查询高并发：性能建模提供对外的DSL语言模拟算子，在建模过程中会计算大量指令，指令调度与计算耗时影响算子建模易用性，需考虑跨语言调用更快速地调度算法。 |

**解读**：将 §3.1 的三大设计目标精准映射到三类工程模型：实现模型解决"指令扩展性"问题（对应 INSTR_TASK 工厂模式注册）；交互模型解决"流水耗时计算统一"问题（对应 PROF_DATA 通过 PrefModel 接口统一 size/time 输出）；并发模型解决"跨语言调度延迟"问题（对应 INSTR_SCHEDULE 任务调度性能要求）。

### 表 4：§4.1.1.3 软件单元清单汇总表

| 软件单元 | 描述 | 外部接口 | 内部接口 | 关系描述 |
|---|---|---|---|---|
| INSTR_TASK | 指令任务创建模块，内部实现 | Tensor、Chip、Core指令 | RawTask | 拆解外部输入指令，形成指令任务集 |
| INSTR_SCHEDULE | 指令调度模块，内部实现 | — | add_task、run | 添加拆解的任务形成任务队列，并模拟芯片行为调度指令 |
| PROF_DATA | 指令性能数据计算，内部实现 | — | prof_data | 根据指令类型加载不同指令的计算结果 |
| TRACE | 指令流水图，内部实现 | — | Trace | 根据指令调度结果，生成指令流水图 |
| METRICS | 指令性能数据，内部实现 | — | Metrics | 根据指令调度结果，生成多种指令性能数据 |

**解读**：INSTR_TASK 是唯一对外暴露接口（Tensor/Chip/Core 指令）的模块，承担外部 DSL 接入职责；其余 4 个模块均为内部实现，对外仅暴露内部接口名（add_task/run、prof_data、Trace、Metrics）。这一设计形成清晰"单向漏斗"——外部指令只从 INSTR_TASK 进入，调度结果再分发到两类产出模块（TRACE 与 METRICS）。

## 【关联】

根据文档上下文与文末提供的内部链接占位符（`arg1, arg2, ..., x, y, z, a, b, c, problem_shape, a, layout_a, b, layout_b, c, layout_c`），可推断出以下上下游关系：

- **DSL → INSTR_TASK**：外部用户（A）通过接口 `a` 输入 DSL 指令（含算子参数 `arg1, arg2, ...`），由 INSTR_TASK 拆解为指令任务；其中的 tensor 形状由 `problem_shape` 携带，而 `layout_a / layout_b / layout_c` 分别对应输入 a、b、c 的数据排布，直接影响搬运通路与 Cache 命中率建模结果。
- **INSTR_TASK → INSTR_SCHEDULE**：拆解后的指令（`x, y, z` 等）以 `RawTask` 形态注入调度队列，由 `add_task` / `run` 接口驱动调度。
- **PROF_DATA ↔ INSTR_SCHEDULE**：PROF_DATA 按指令类型提供耗时数据；`PrefModel.get(api_name)` 在调度时被调用，影响 `cost_time()` 计算。
- **INSTR_SCHEDULE → TRACE / METRICS**：调度完成后产出可视化（指令流水图）与统计图表（指令占比饼图、指令信息统计），二者均依赖"调度起止时间"这一公共结果。
- **自动寻优链路**：模板库下发代码生成 → 编译 → 运行 → kernel 性能度量 → msopgen 工程轻量化调度，构成 msKPP 与外部模板库、msopgen 工程、kernel 调优工具的协同闭环。
