# MindStudio Profiler Analyze 特性分析与设计说明书 — 一体化深度解读

---

## 【定位】

本篇文档是 MindStudio Profiler Analyze（msprof-analyze）面向 MindStudio 26.0.0 版本的设计说明书,系统阐述该性能分析工具的**模型性能拆解比对**与 **Host Bound 自动识别**两大核心能力,并给出 Host Bound 识别的完整实现流程与安全/DFX 设计基线。

---

## 【技术要点】

1. **产品定位与所属 SIG**：msprof-analyze 是 MindStudio 全流程工具链推出的性能分析工具,基于采集到的性能数据进行分析,识别 AI 作业中的性能瓶颈;所属 SIG 组为 `mstt-sig`,落入版本 MindStudio 26.0.0,初稿作者与审核人均为 chenhao(日期 2026.01.21)。

2. **两大核心需求**(对应表 1 特性需求列表):
   - **需求 1 — 模型性能拆解比对能力**:模型算子的拆解和比对能力分析报告。
   - **需求 2 — Host 分析能力**:Host Bound 性能问题的自动化识别能力。

3. **硬件支持范围**(原文 2.3.1 硬件限制表):**昇腾 A3 系列产品**与**昇腾 A2 系列产品**均支持。

4. **技术栈约束**(原文 2.3.2 技术限制):操作系统仅 `linux`;编程语言为 `C / Python`;平台差异性分析为 `win/linux`。

5. **Host Bound 识别流程的关键算法步骤**(原文 4.3 详细实现):
   - 先**计算并筛选 NPU 硬件的闲置时间**,关注"大块闲置时间"。
   - 对大块闲置时间,**归类瓶颈层级**为 **Host 侧瓶颈**或 **Device 侧瓶颈**;Host 侧关注 PyTorch 层与 CANN 层下发任务,Device 侧关注设备侧任务。
   - **Host 侧瓶颈**:取前后两个邻近硬件任务及其主机侧 CANN/PyTorch 下发,基于层间等待时间构建行为模式,给出耗时最长的 PyTorch 函数与 CANN 层函数。
   - **Device 侧瓶颈**:综合考虑区间内操作的延时和操作频率,推选**综合延时最大的操作**作为瓶颈。
   - **通信算子场景**会进一步触发**多卡联动分析**:聚合通信域内所有卡的通信执行时间,识别**最快卡**与**最慢卡**并对齐其通信任务结束时间(用于调整卡间时钟漂移),再在慢卡等待快卡期间比对相同任务间的延时差异,推选延时差异最大的操作作为慢卡瓶颈。

6. **安全设计基线**:新增侦听端口、新增进程间通信、新增认证方式、新增 GUC 参数等项均**不涉及**;**涉及且满足**的项为:涉及创建文件或目录(显式指定访问权限)、新增/修改函数视图/系统表(刷新产品文档并考虑权限控制)、新增内部工具(刷新产品文档)。

## 【关键机制与数据】

### 工作原理与数据流(基于原文 4.3 详细实现)

**整体方案**(原文 §3.2):msprof-analyze 基于**采集到的性能数据**做离线分析,识别 AI 作业瓶颈——属于"采集—分析"分离的离线工具,而非在线剖析器。

**Host Bound 识别五步工作流**(原文 §4.3,图 3):

| 阶段 | 原文机制描述 | 作用 |
|---|---|---|
| ① 闲置识别 | "计算并筛选 NPU 硬件的闲置时间,关注某个大块闲置时间" | 把瓶颈定位到时间窗口 |
| ② 层级归类 | "明确其性能瓶颈所在层级,归类为 Host 侧瓶颈,将设备层的问题归为 Device 侧瓶颈" | 把时间窗口映射到责任方 |
| ②.1 邻近任务采样 | "关注当前大块闲置时间邻近的前后两个硬件任务,及其主机侧的 CANN 层下发操作和 PyTorch 层的下发任务" | 取上下文窗口 |
| ②.2 层间等待计算 | "基于邻近两个硬件任务的主机侧下发和硬件侧执行行为,分别计算层间的等待时间"(图 image_3) | 量化各层阻塞贡献 |
| ②.3 行为模式构建 | "根据前后邻近任务的层间等待时间,构建当前行为模式"(图 image_4) | 把数值转成可判定的模式 |
| ③ Host 侧瓶颈定位 | "关注前后邻近任务之间发生的所有 PyTorch 层和 CANN 层任务,给出耗时最长的 PyTorch 函数与 CANN 层函数" | 输出 Top-N Host 侧函数 |
| ④ Device 侧瓶颈定位 | "综合考虑这些操作的延时和操作频率,计算其综合延时,推选出综合延时最大的操作作为性能瓶颈操作" | 用 **延时 × 频率** 的综合指标选瓶颈算子 |
| ⑤ 通信算子级联 | "若当前性能瓶颈被认定为通信算子任务,则对该通信任务进行多卡联动分析" | 单卡瓶颈 → 集群级归因 |
| ⑤.1 时钟对齐 | "聚合通信算子任务的通信域内所有卡的通信执行时间,找到最快卡和最慢卡……并对齐快慢卡的通信任务结束时间,以调整卡间的时钟漂移"(图 image_5) | 解决多卡时间基准不一致 |
| ⑤.2 慢卡瓶颈 | "关注慢卡在快卡等待期间的任务……比对相同任务间的延时差异,推选出延时差异最大的操作任务,作为慢卡的瓶颈操作"(图 image_6) | 在时间对齐后做差分定位 |

**性能影响**(原文 §4.6.1):"新增模块的分析能力,局部计算节点的数据对比及识别,性能影响可控"——即分析本身是局部、可控开销,不要求高规格资源。

**性能/资源规格**(原文 §2.3.4):"按需配比资源,无特定规格诉求"。

> 原文未给出具体性能数字(如端到端分析耗时、内存峰值、加速比等),也未给出 API/CLI 形式的数据输入格式规范,故不在此臆造。
