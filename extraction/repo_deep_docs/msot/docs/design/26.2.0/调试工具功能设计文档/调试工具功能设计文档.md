# MindStudio Debugger 功能设计说明书 —— 深度解读

---

## 【定位】

本文档是 MindStudio Debugger (msot) 的功能设计说明书，旨在为 NPU（Neural-network Processing Unit）算子开发设计一款类比 CPU 领域 GDB/LLDB 的调试工具，专门解决当前 NPU 算子上板调试中"黑盒化"、AI Core 崩溃难定位、L0 内存/寄存器不可见、printf 风格打印易用性低等痛点，把算子开发从"猜错"转变为"查错"。

---

## 【技术要点】

1. **适用范围与硬件目标**：当前目标仅针对 AI Core 算子调试，覆盖 **910B、950、310P** 三款芯片；非目标包括 AI CPU/CPU 程序调试以及 core 文件的生成；每次只能对单张卡做调试。
2. **总体架构（三层 Client/Server + 劫持库）**：基于 **LLDB 源码二次开发**（选择 LLDB 的原因是 GDB 开源协议不适合商用），由三个核心组件构成——**调试客户端 (Client)** 解析命令与 ELF 调试信息并通过 **socket-pair** 与 Server 通信；**调试服务端 (Server)** 通过 **ioctl** 与驱动通信，控制 AI Core 执行状态；**Preload Dynamic Library** 劫持 `SetDevice`、`Register Kernel Object`、`Launch Kernel Object` 等 runtime 桩函数以获取 pid、device_id、kernel object 等信息。
3. **环境与编译约束**：**Linux Host** 主机；**NPU Driver v26.0+**；核心引擎使用 **C++**；被调试算子二进制必须带 **`-g (DWARF) -O0`** 调试信息（这是关键硬约束）。
4. **核心调试能力（10 类）**：包括程序控制类（断点设置/单步调试/恢复运行/中断运行）、信息打印类（变量/寄存器/内存/上下文切换/状态信息展示/调用栈回溯）、core 文件解析。其中 **硬断点只用于 simt vf/simd vf 且个数不超过 4 个**；打印内存支持 **UB, GM, L0A, L0B, L0C** 等多种类型；不支持表达式计算打印。
5. **安全与可靠性设计**：使用调试功能需 **root 用户打开驱动通道开关**（`echo 1 > /proc/debug_switch`）；`DeviceContext` 类可派生子类屏蔽底层硬件差异；劫持库**不改变用户算子行为，仅做信息收取**，保证被调试程序的语义等价性。
6. **已知风险与限制**：当前需要 Simt/Simd VF 函数，无法做到 O0 优化（这是一个看起来与上面"O0 必须"略有矛盾、但实际表达"需要避免被进一步优化"语义的细节），部分代码行可能无法断住；调用栈回溯在 simt_vf/simd_vf 断点上不会展示 main scalar 上的栈，main scalar 调用栈不会展示 host 侧代码。

---

## 【关键机制与数据】

**工作原理与数据流（原文: §3.1 总体方案）**：

- **客户端 (Client)**：负责解析用户输入的命令，解析 ELF 里的调试信息（DWARF），把简化后的命令通过 **socket-pair 进程间通信** 发送给 Server 侧。
- **服务端 (Server)**：负责与驱动通信，通过 **ioctl** 把控制消息发送到驱动，获取或控制 NPU 设备上 AI Core 的执行状态；接收劫持库发送的 **pid, device_id, kernel object** 等信息。
- **Preload Dynamic Library**：实现 runtime 的桩函数（stub），通过劫持 `SetDevice`、`Register Kernel Object`、`Launch Kernel Object` 等函数，获取相应的运行时信息，并发送给工具侧。
- **整体架构图**：原文引用 `./images/solution_arch.png`（缩放 80%）描述三组件关系。

**结构体/接口定义（原文: §3.4.2）**：

- 控制 AI Core 执行状态的结构体定义设计参考外部 **arch 文档**（https://gitcode.com/Ascend/msdebug/blob/master/docs/zh/development_guide/architecture.md）。
- Coredump 文件的结构体定义参考同一文档的 §4.3.1.2 关键字段说明小节。

**DFX 与质量设计要点（原文: §3.3）**：

- **安全**：root 用户打开 `/proc/debug_switch` 通道开关。
- **可维护性**：`DeviceContext` 类派生子类屏蔽硬件差异。
- **可靠性**：劫持库不改变用户算子行为。
- **可测试性**：交互式测试用例 + UT。

**性能/规模相关数字（原文有的）**：硬断点 **≤ 4 个**；调试通道开关路径为 `/proc/debug_switch`；Driver 版本下限 **v26.0+**。

## 【表格解读】

### 表格 1：用例分析（§2 原文）

| 场景描述 | 功能清单 | 功能描述 | 限制 |
|---|---|---|---|
| 程序控制 | 断点设置 | 软、硬断点增删管理，其中硬断点只用于simt vf/simd vf | 硬断点只用于simt vf/simd vf, 个数不超过4个; |
| 程序控制 | 单步调试 | step over: 代码行级别单行往下运行; step in: 进入函数 ; step out: 跳出函数 | NA |
| 程序控制 | 恢复运行 | 用于命中断点后的恢复运行，让程序继续运行下去 | NA |
| 程序控制 | 中断运行 | 用于程序卡死在device侧时, 中断运行后查看卡死的代码行位置 | 中断后只支持查看调用栈和上下文切换功能 |
| 信息打印 | 打印变量 | 打印变量的内容，会根据变量类型展示对应的结构体成员, 支持在host代码上打印申请的GM变量内容 | 不支持表达式计算的打印 |
| 信息打印 | 打印寄存器 | 打印寄存器的内容 | NA |
| 信息打印 | 打印内存 | 打印不同类型的内存数据，包括UB,GM,L0A,L0B,L0C等 | NA |
| 信息打印 | 上下文切换 | AI Core之间切换，或者Simt vf 里的线程切换，与配合状态信息展示功能或程序控制类功能配合使用 | NA |
| 信息打印 | 状态信息展示 | 展示当前算子使用到的AI Core、Block、Device、Task、Stream、Thread等信息；展示当前AI Core停住位置的代码行信息 | NA |
| 信息打印 | 调用栈回溯 | 展示当前AI Core所在代码行的调用栈 | simt_vf, simd_vf下断点的调用栈不会展示main scalar上；main scalar上的调用栈不会展示出host侧代码 |
| core文件解析 | 信息打印场景所有功能 | 包含上述所有信息打印场景下的所有功能 | NA |

**逐行解读**：

- **断点设置**：唯一带"硬断点上限"数字（**≤4**）的行，明确硬断点只服务于 simt vf/simd vf 两种向量函数。
- **单步调试**：标准 GDB 语义（step over/in/out），无限制。
- **恢复运行**：断点命中后的 continue 类操作。
- **中断运行**：针对 device 侧卡死的应急入口；限制是**只能查看调用栈 + 上下文切换**，不能做其他操作，说明中断后程序状态被冻结，不能继续执行。
- **打印变量**：唯一明确支持"host 代码上打印 GM 变量内容"的能力扩展；不支持表达式计算是显著的功能缺口（与 GDB `print expr` 不同）。
- **打印寄存器**：直接对应文档动机中"printf 不支持寄存器值"的痛点解决。
- **打印内存**：覆盖 **UB / GM / L0A / L0B / L0C** 五种典型 NPU 内存类型——尤其 L0A/B/C 是 AI Core 内部高性能 buffer，是本次调试能力的关键补齐。
- **上下文切换**：双层切换——AI Core 之间切换 + Simt vf 内线程切换，是多核多线程调试的入口。
- **状态信息展示**：覆盖 **AI Core / Block / Device / Task / Stream / Thread** 六维硬件/调度状态，配合代码行定位。
- **调用栈回溯**：明确指出两类栈显示边界——simt_vf/simd_vf 断点看不到 main scalar 上的栈；main scalar 的栈看不到 host 代码。这是一个**已知的栈拼接缺口**。
- **core 文件解析**：复用信息打印场景所有功能，是离线场景。

### 表格 2：测试设计（§4 原文）

| 测试类型 | 算子场景 | 描述 | 示例 |
|---|---|---|---|
| 单元测试 | NA | 测试Server测功能函数 | HandleStubDevice测试能否处理收到的device_id信息 |
| E2E测试 | Simt算子 | 测试上述所有功能是否成功 | 断点设置在simt算子里，能否恢复运行，变量打印等功能 |
| E2E测试 | Simd算子 | 测试上述所有功能是否成功 | 断点设置在simd算子里，能否恢复运行，变量打印等功能 |
| E2E测试 | cube算子 | 测试上述所有功能是否成功 | 断点设置在simd算子里，能否恢复运行，变量打印等功能 |

**逐行解读**：

- **单元测试**：仅覆盖 Server 侧（原文用词为"Server 测功能函数"，疑似"Server 端"笔误）；以 `HandleStubDevice` 接收 device_id 的处理为典型示例。
- **E2E 测试**：覆盖 NPU 算子的三大典型范式——**Simt（标量多线程）**、**Simd（向量）**、**Cube（矩阵）**。
- **一个细节问题**：表格中 cube 算子测试示例写的是"断点设置在 simd 算子里"（疑似笔误，与"cube 算子"场景描述不一致），原文未修订，应视为原文瑕疵记录在案。

## 【使用方法】

原文（§3.4.3 使用说明）给出了完整启用流程：

1. **编译算子**：确保编译时加入 **`-g -O0`** 选项保留调试符号（DWARF + 关闭优化）。
2. **打开驱动通道**：以 root 用户执行
   ```
   echo 1 > /proc/debug_switch
   ```
3. **启动调试器**：执行
   ```
   msdebug <app>
   ```
   进入交互界面后输入
   ```
   b <file_name>:<line_no>
   ```
   设置断点，然后 `run` 启动被调试程序。

其他使用细节（特定命令语法、上下文切换指令、core 文件加载方式等）原文未涉及。
