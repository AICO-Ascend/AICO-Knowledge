# 「算子调试工具功能设计文档」(msdebug · coredump 解析) 深度解读

---

## 【定位】

本文档描述 msdebug 算子调试工具对 **算子 coredump 文件解析**能力的功能设计,通过在 coredump 文件中新增若干 .ascend.* 段并在 msdebug 中加载该文件,使后续所有查询命令基于已恢复的进程现场数据展示,**无需复现现场即可定位现网挂死问题**。

---

## 【技术要点】

1. **整体定位**:msdebug 是与 cuda-gdb 对标的昇腾 AI 处理器上板单步调试工具,属 CANN 架构元素下的调试器模块,复用 LLDB 整体架构(LLDB Client/LLDB Server 形态),并通过 SQCQ 通道与 TSFW、ts_debug.ko 与 device driver 协同。
2. **支持硬件范围**:A2、A3、310P、A5;硬件/技术边界受限于 Driver、RTS 能力与编译器能提供的 DWARF 调试信息。
3. **核心新增能力**:coredump 解析,命令行为 `msdebug --core core.file` 或 `(msdebug) target create --core core.file`(对标友商 `(cuda-gdb) target cudacore core.file`)。
4. **运行环境**:coredump 文件解析可在**无 NPU 驱动环境**上运行;系统性能侧需内存足以加载 coredump 文件;License 与系统兼容性"不涉及"。
5. **coredump 文件结构**:复用 ELF 扩展,在标准 ELF header/text/data 等段之外新增 `.ascend.devtbl / .ascend.global / .ascend.local.{core_id} / .ascend.regs.{core_id} / .ascend.auxinfo.global / .ascend.auxinfo.local.{core_id}` 等段,并加入进程加载后恢复现场所需信息(全局设备表、kernel 占用 GM 内存内容、每 AI core local memory 与寄存器现场等)。
6. **PC 修复机制**:由于 coredump 时刻 PC 可能不正确,工具内部结合 AIC_ERROR_0..5 与对应类型名 (MTE/IFU/CUBE/CCU/VEC/FIXP) 的 ERR_INFO 寄存器位字段替换 PC 中的位(0-7 与 16-23 位),以恢复准确 PC。
7. **架构交互**:涉及编译器、msdebug、运行时 RTS、`ts_debug.ko`、TSFW 多方;通过对 DEBUGGER_API 的扩展可分别实现断点设置、恢复/单步运行、内存/寄存器读取等功能并支持后续功能扩展。

---

## 【关键机制与数据】

### 1. 总体架构与命令流(原文 §3.2 figure3)

整体复用 LLDB,组件协同流程(原文所述,16 步):

> 1. 拉起用户进程,在子进程中设置 LD_PRELOAD,使能桩函数,并阻塞(原生机制)子进程
> 2. 用户在 LLDB 中设置断点,并保存信息(此时未真正下发断点到设备)
> 3. LLDB 通知用户程序运行(原生机制)
> 4. 当用户运行到 set device 时,通过接口的劫持,使得 device Id 上报到了 LLDB
> 5. LLDB 通过 SQCQ 通道给 TS 下发 set debug,使得 TS 进入 debug 模式
> 6. 当 TS 在 debug 模式下收到 task 时,通过 SQCQ 通道上报 event,并返回 base 地址和 deviceId
> 7. LLDB 通过驱动的共享空间在 device 的 kernel 上覆写软断点指令
> 8. LLDB 通过 SQCQ 通知 TS 断点设置行为,TS 需要设置 icache 的缓存失效
> 9. LLDB 通知 TS 继续执行
> 10. TS 通过 SQCQ 上报**断点命中信息**,并停止对应核的指令调度
> 11. LLDB 通过驱动申请 GM 内存
> 12. LLDB 通过 SQCQ 通道通知 TS 将片上内存搬运到其申请的 GM 内存
> 13. LLDB 将 GM 内存中的信息拷贝到 host 侧,并显示
> 14. LLDB 将原断点指令恢复
> 15. LLDB 通过 SQCQ 通知 TS 进行 single step
> 16. LLDB 通过驱动接口重新覆写软断点 → LLDB 通过 SQCQ 通知 TS 程序继续运行

性能/容量数据(原文提供):

- 设备 core 数表征:`aic_bitmap0/1`、`aiv_bitmap0/1` 各 64 bit,合计 256 bit,即"考虑以后可能同个类型核超过 64 个,需要多个 bitmap"。
- PC 修复规则中位字段:`INFO` 寄存器的 **0-7 位替换 PC 寄存器的 0-7 位,16-23 替换 16-23 位**(原文)。

### 2. coredump 文件 → 进程现场恢复流程(原文 §4.1 figure5)

> 1. 用户使用 --core 参数加载 coredump file
> 2. 命令行识别到存在 coredump file 后,需通过识别 core file elf header 结构,会创建 cpu 上的 ProcessElfCore 实例,还是 npu 上的 ProcessElfCore 实例,ProcessElfCore 自身会对 coredump file 进行解析加载,恢复进程现场。

### 3. PC 修复算法(原文)

> 先查询 AIC_ERROR_0/1/2/3/4/5 的值,获取其 bit 位,判断是 mte/ifu/cube/ccu/vec/fixp 中哪种类型。每次只会命中一种错误,如果多种,目前就选择任意一种。再查询类型名对应寄存器,{MTE/IFU/CUBE/CCU/VEC/FIXP}_ERR_INFO 寄存器,替换当前 PC 寄存器里的某几位。比如 INFO 寄存器里的 0-7 替换 PC 寄存器里的 0-7,16-23 替换 16-23 位。

### 表 3:新增 coredump 段含义对照(原文 §4.3)

| 段名 | 简要含义 |
|---|---|
| elf header | 其中应包含能识别是否 npu device 架构的信息 |
| .ascend.devtbl | 全局设备信息,考虑到不同架构上的寄存器、内存类型可能不同,这里需要保存当时的设备类型,用到哪些 ai core 等信息 |
| .ascend.global | 用于记录 kernel 在 gm 上占用的内存信息 |
| .ascend.local.{core_id} | 用于记录每个 ai core 在 local memory 的内容,内存类型不同也会分不同段,内存类型的描述在 auxinfo 里 |
| .ascend.regs.{core_id} | 用于记录每个 ai core 拥有的寄存器的值 |
| .ascend.auxinfo.global | 用于描述每段 global 内存的业务属性 |
| .ascend.auxinfo.local.{core_id} | 用于描述每段 local 内存的业务属性 |

**解读**:
- `elf header` 段用来判别文件是否属于 NPU device 的 coredump,后续据此创建 cpu 或 npu 侧的 `ProcessElfCore`。
- `.ascend.devtbl` 在表后结构体定义为关键索引(`DevInfo`),承载设备类型/AI core 使用位图,采用 `aic_bitmap0/1`、`aiv_bitmap0/1` 的多 bitmap 方案以支持 ≥64 核。
- `.ascend.global` 与 `.ascend.auxinfo.global` 配合:**前者连续放多段 section 数据,后者承载索引与业务属性**(对应原文 `GlobalMemInfo` 结构体,见 §4.4 接口设计),目的是兼容"GM 内存可能不连续"与"将来需取 kernel 输入"的需求。
- `.ascend.local.{core_id}` 与 `.ascend.auxinfo.local.{core_id}` 配对:`.ascend.local` 全量解析存储不同内存类型数据(原文:基于 addr 可省略、core_id 只需出现一次、内存类型需区分三点);auxinfo 段保存索引(对应 `LocalMemInfo`)。
- `.ascend.regs.{core_id}` 由多个 `REG_Entry` 组成(对应 `RegInfo` 结构体),考虑"寄存器大小可能不同、地址全局唯一",逐 entry 解析。

## 【公式解读】

> 原文无 LaTeX 数学公式或伪代码公式,仅给出 PC 恢复算法描述(见 §关键机制与数据 §3)。如需以伪代码表达:

```text
PC' = PC;
err_bits = AIC_ERROR_0 | AIC_ERROR_1 | AIC_ERROR_2 | AIC_ERROR_3 | AIC_ERROR_4 | AIC_ERROR_5;
type = decode_error_type(err_bits);   // ∈ {MTE, IFU, CUBE, CCU, VEC, FIXP}
INFO = ERR_INFO_REG(type);            // 对应 {MTE/IFU/CUBE/CCU/VEC/FIXP}_ERR_INFO 寄存器值
PC'[0:7]  = INFO[0:7];                // 原: 0-7 → 0-7
PC'[16:23] = INFO[16:23];             // 原: 16-23 → 16-23
```

符号说明:

- `PC`:原始 PC 寄存器值(原文中,coredump 时刻可能不正确)。
- `AIC_ERROR_0..5`:错误类型寄存器,bit 位区分 mte/ifu/cube/ccu/vec/fixp,每次只命中一种。
- `type`:当前错误类型。
- `INFO`:对应错误类型的 ERR_INFO 寄存器。
- `PC'` 字段替换规则(原文):`INFO` 的 `[0:7]` 替换 `PC` 的 `[0:7]`,`[16:23]` 替换 `[16:23]`。

> 原文给出以下与 coredump 解析直接相关的启用方式与命令形式:

- **命令(对标友商)**:`(cuda-gdb) target cudacore core.file`

## 1) 图的内容
该图描绘了ELF（可执行与可链接格式）文件的内存布局结构，自上而下依次为：**ELF header**、**Program header table**、**.text**（代码段）、**.rodata**（只读数据）、**...**、**.data**（可写数据）、**Section header table**。箭头标注了两种header table与各section之间的索引引用关系。

## 2) 论证的技术结论
- **双重索引机制**：Program header table描述段（segment）的运行时映射，Section header table描述节（section）的链接视图，二者各司其职。
- **权限分离**：.text与.rodata位于只读映射区，.data位于可读写映射区，体现内存保护设计。
- **结构定位**：ELF header位于文件首，Section header table位于文件尾，便于解析器双向读取。

## 3) 与文档论点的关系
作为算子调试工具的设计文档，该图为调试器（DAP/GDB类）解析算子二进制（如.so/.o）的**运行时内存视图与符号定位**提供了底层格式依据，是实现断点设置、变量查看、单步跟踪等调试功能的结构基础。
