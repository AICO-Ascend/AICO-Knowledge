# MindStudio Sanitizer (mssanitizer) 功能设计文档 · 一体化解读

---

## 【定位】

本文档定义昇腾芯片算子开发场景下的 **MindStudio Sanitizer (mssanitizer) 检测工具** 在新版本中的 6 项新增能力：覆盖 aicpu tiling 越界写检测、跨卡共享内存竞争检测、msTx 内存属性检测、950 硬件代际的同步/初始化检测扩展、以及 wait_flag 死锁检测,目标是帮助开发者在 AscendC / Triton / CATLASS / SHMEM 等算子开发中快速识别并定位内存越界、内存对齐、内存初始化、多核/跨卡流水竞争等问题。

---

## 【技术要点】

1. **aicpu tiling 越界写检测**(非插桩方案)——由于 aicpu 编译器暂不支持指令插桩,通过在每个 GM buffer **前后增加安全区**的方式实现;在 kernel 运行结束时遍历所有 GM buffer 检查安全区是否被污染,识别越界写;执行下一个 kernel 前还原安全区。命令行参数 `--padding <size>`,默认值 **32**。

2. **跨卡共享内存竞争检测**——扩展原核间竞争检测算法到多卡场景(把不同卡上同名 kernel 的运行记录按"多核展开"形式纳入竞争检测算法);由于软同步由 LD/ST 指令组合、指令本身不带同步语义,要求算子通过 **msTx 接口**完成同步语义上报;只检测标记为"共享内存"的 buffer,非共享内存记录直接过滤。命令行参数 `--cross-npu-check <yes/no>`,默认值 **no**。

3. **msTx 接口指定内存属性检测**——通过 msTx 接口上报 buffer 属性,mssanitizer 把该属性加入内存区间的合法性判断;支持 5 类属性:**只读 / 只可写 / 可读写 / 不可读写 / 可读写共享内存**;不满足属性时上抛 **illegal read/write** 告警。兼容性约束:未使用 msTx 接口时默认属性为"可读写"。

4. **950 代际同步检测**——**冗余 set_flag 识别算法沿用 A2/A3 代际**;同时扩展新硬件 **SIMT 架构**下的 `sync_threads` 检测:要求每条 `sync_threads` 必须被每个线程遍历到,未满足则在 kernel 结束后提示该 `sync_threads` 的具体代码行。

5. **950 代际初始化检测**——读未初始化内存识别算法沿用 A2/A3 代际;需要把 SIMT 模块的内存读写行为通过 **在线 shadow memory 检测算法** 完整记录后,插入到外部 SIMD 检测流程中,识别读未初始化内存并展示读指令对应的代码行。

6. **wait_flag 死锁检测**——支持两种退出机制保证算子可从卡死状态退出:
   - **超时时间**:通过劫持流同步接口为算子配置超时时间。
   - **Ctrl+C 退出**:通过捕获 SIGINT 信号量,强制终止算子所在 stream。
   算子退出后**重放已记录的同步指令**,无法正常调度即判定卡死,再遍历各 pipe 检查是否存在无法调度的 `wait_flag`,抛出死锁告警;**仅支持检测卡死在 wait_flag 的场景**,while 死循环等不检测。

## 【关键机制与数据】

- **aicpu 检测数据流**(原文 3.1.1):kernel 结束 → 遍历所有 GM buffer → 检查 buffer 前后安全区是否被污染 → 若污染即上抛越界写告警 → 下个 kernel 启动前还原安全区。检测粒度为 "kernel 运行结束后"的批量比对,不指示代码行(因编译器未支持插桩)。

- **跨卡竞争检测工作流**(原文 3.1.2):NPU1 的 kernel A 写 GM 共享内存 → 改 flag 通知 NPU2 → NPU2 上同一 kernel A 轮询 flag → 通过软同步完成卡间同步。**正确用软同步 ②**;若用错,①与④出现"读后写竞争"。`figures/cross_npu_race_check.png` 图示示意此链路(原文为图片描述,无可量化数据)。

- **SIMT 与 SIMD 检测融合**(原文 3.2.5):通过在线 shadow memory 检测算法把 **SIMT 模块的内存读写行为** 完整记录,**插入**到外部 SIMD 检测流程——表明 950 代际并非单独自建一套检测,而是把 SIMT 通道汇入既有的 SIMD 检测流水线。

- **参考算法**(原文第 6 节):内存检测算法参考 **valgrind**,采用 **shadow memory 维护内存状态**——意味着 mssanitizer 沿用 shadow memory 思路,而非另起炉灶。

- **检测结果输出维度**(原文 2.2):竞争检测识别并提示**竞争类型、kernel 名、device id、出现数据竞争的指令代码行**。

- **死锁检测告警信息**(原文 2.6):超时后可识别到卡死在**哪个 wait_flag 指令**,并展示**对应代码行**;同步指令记录写入日志,可支持维护查询。

## 【关联】

文档未提供文末内部链接,但文内多次引用外部仓与既有代际,以下为可识别的关联链路:

- **aicpu tiling 下发方式**——参考 `https://gitcode.com/cann/asc-devkit` 下 `examples/01_simd_cpp_api/02_features/04_aicpu/aicpu_device_tiling/README.md`,即 AscendC 通过 `<<<>>>` 语法把 tiling 函数下发到 aicpu(原文 2.1)。本能力仅在不依赖 aicpu 编译器插桩的前提下提供,因此**与 aicore kernel 的逐指令插桩检测能力不重合**——aicore 能精确到代码行,aicpu tiling 只能在 kernel 结束后识别越界写(原文 1.3)。

- **SHMEM 算子样例**——参考 `https://gitcode.com/cann/shmem` 下 `examples/allgather_matmul/README.md`(原文 2.2),即跨卡共享内存通信的入口。文档将 shmem 库的卡间同步流程 `figures/cross_npu_race_check.png` 接入 mssanitizer。

- **代际演进关系**——A2/A3 代际算法(`冗余 set_flag` 识别、读未初始化内存识别算法)被**直接沿用**到 950 代际(原文 3.2.4、3.2.5);950 代际同步检测类型与初始化检测类型应**覆盖**A2/A3 代际(原文 3.3.4、3.3.5)。

- **msTx 接口**——是 mssanitizer 在跨卡竞争检测与内存属性检测两条能力上的**共同依赖**:竞争检测需要 msTx 报同步语义,内存属性检测需要 msTx 报 buffer 属性(原文 3.1.2、3.2.3),两者都通过"算子端接口上报 + sanitizer 端消费上报信息"形成闭环。

- **流同步接口与 SIGINT**——死锁检测依赖 `流同步接口` 进行超时时间劫持,并依赖 `SIGINT 信号量` 捕获(原文 3.2.6),把 mssanitizer 与 CANN 运行时 / OS 信号机制耦合在一起。

- **测试范围联动**(原文 4.2 测试矩阵):算子类型 mix/cube/vec/simt × 编程语言 AscendC/Triton/CATLASS/SHMEM × 调起方式 `<<<>>>`/ACLNN/PTA × 款型 A2/A3/950——表明 6 项能力均需在该四维矩阵中找到对应测试组合,6.1 至 6.6 各自再增加一句具体场景构造指引。

## 【使用方法】

**启用方式总览**:mssanitizer 提供 **命令行 CLI**(原文 3.4.1),不需要在算子中新增 API 调用,开发环境直接使用 CANN 环境即可;6 项能力彼此独立,通过新增 CLI 参数启用。

**新增 CLI 参数**(原文 3.4.2):

| 参数 | 默认值 | 作用 |
|---|---|---|
| `--padding <size>` | `32` | aicpu tiling 越界写检测的安全区大小,可动态调整以适配首地址较大的场景(原文 3.4.2.1、3.3.1) |
| `--cross-npu-check <yes/no>` | `no` | 启用 shmem 算子的卡间共享内存竞争检测(原文 3.4.2.2) |

**能力 2.3 / 2.4 / 2.5 / 2.6 的启用说明**:
- **msTx 内存属性检测**(原文 3.2.3、3.4 未单列参数)——通过算子侧调用 msTx 接口上报属性触发;**未调用 msTx 时 buffer 属性默认 "可读写"**,与原内存检测兼容。
- **950 代际同步检测 / 初始化检测**(原文 3.2.4、3.2.5)——在 950 硬件上运行 mssanitizer 时自动具备;测试分别在 `vector / cube / mix` 算子类型上构造 "冗余 set_flag" 与 "读未初始化内存" 场景触发(原文 4.3.4、4.3.5)。
- **同步死锁检测**(原文 3.2.6)——通过 **超时时间 + Ctrl+C** 两种机制触发:超时由 mssanitizer 劫持流同步接口配置;Ctrl+C 由 SIGINT 信号量捕获,强制终止算子所在 stream。

**配置项 / 命令**——`--padding <size>` 与 `--cross-npu-check <yes/no>` 两个新增参数**均不影响原有参数**(原文 3.4.3);CLI 由 mssanitizer 自身提供,不依赖 CANN 之外的额外配置项。

**未涉及内容**(原文未出现):CLI 完整使用示例、msTx 接口的具体函数签名、aicpu `<<<>>>` 调用规范、PTA / ACLNN 调起方式下的差异化参数、950 款型识别机制——以上均需查阅 CANN / AscendC 配套文档或仓库 README。

## 图文联合解读

- `aicpu_sanitizer.png`: **图文联合解读：**

1. **图示内容**：GM buffer（蓝色）尾部紧邻绿色"安全区"，下方黄色"GM write"箭头向上写入，红线标注"越界写"穿过了buffer边界进入安全区。

2. **技术结论**：当aicpu tiling函数对GM buffer执行写操作时，若写入长度超过buffer实际范围，会越界覆盖安全区甚至其他kernel的GM buffer，mssanitizer需在tiling函数运行结束后识别此类越界写行为。

3. **与文档关系**：图示直接对应1.2.1节动机——aicpu tiling函数越界写检测场景的可视化说明，佐证该功能的设计必要性与检测对象。
- `cross_npu_race_check.png`: **图文联合解读：**

图示展示NPU1与NPU2同时运行同一Kernel A，通过共享GM内存（data/flag区）交互：NPU1经MOV_UB_2_GM写data区（①）、ST写flag区（②）；NPU2在sync同步块内的LOOP中LD读flag（③）作为等待信号，MOV_GM_2_UB读data（④）。该图论证了shmem算子卡间通过flag进行同步、读写共享内存的典型数据流模式，正是1.2.2节所述"卡间共享内存竞争检测"的检测对象——不同卡上相同kernel对标记为共享内存buffer的读写指令，存在race风险时需mssanitizer介入识别。
