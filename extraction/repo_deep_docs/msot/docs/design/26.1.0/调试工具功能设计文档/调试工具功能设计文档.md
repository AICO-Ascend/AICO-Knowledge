# MindStudio Debugger 功能设计说明书 — 一体化深度解读

---

## 【定位】

这篇文档设计并规划了一款**面向 NPU (Neural-network Processing Unit) 算子开发的专用调试工具 MindStudio Debugger (msdebug)**,类比 CPU 领域的 GDB/LLDB, 解决 NPU 算子开发"黑盒化"、调试手段匮乏的痛点, 提供断点、单步、变量/寄存器/内存查看、Core 文件解析、多核状态可视化等能力, 将"猜错"变为"查错"。

---

## 【技术要点】

1. **架构基础**: 基于 LLDB 源码进行二次开发 (GDB 开源协议不适合商用, 故选 LLDB), 沿用 Client-Server 结构, 整体由 **调试客户端 Client / 调试服务端 Server / 动态劫持库 Preload Dynamic Library** 三大核心部件组成。
2. **进程间通信**: Client 与 Server 之间通过 **socket-pair** 方式进行进程间通信, Client 将解析后的简化指令发给 Server。
3. **与驱动通信**: Server 通过 **ioctl** 把控制消息下发给驱动, 实现对 NPU AI Core 执行状态的获取与控制。
4. **劫持机制**: Preload Dynamic Library 实现 runtime 桩函数, 劫持 `SetDevice` / `Register Kernel Object` / `Launch Kernel Object` 等函数, 收集 `pid`、`device_id`、`kernel object` 等信息回传。
5. **支持范围**: AI Core 算子调试只覆盖 **910B / 950 / 310P** 三款芯片; 每次只能对**单张卡**做调试; 非目标包含 AI CPU / CPU 程序调试以及 core 文件的生成。
6. **安全与约束**: 启用调试需 **root 用户**打开 `/proc/debug_switch` 通道开关; 被调试算子二进制必须含 **`-g` (DWARF) 与 `-O0`** 调试信息; 硬断点个数 **不超过 4 个**, 且仅用于 **simt vf / simd vf**。

---

## 【关键机制与数据】

**整体工作流 (原文第 3.4.3 节)**:
1. 用户编译算子时携带 `-g -O0`, 保留 DWARF 调试符号。
2. Root 用户执行 `echo 1 > /proc/debug_switch` 打开驱动调试通道。
3. 执行 `msdebug <app>` 启动调试器, 进入交互界面。
4. 通过 `b <file_name>:<line_no>` 设置断点, `run` 启动程序。
5. Client 解析用户命令与 ELF 中的调试信息, 将简化指令经 socket-pair 投递到 Server。
6. Server 通过 ioctl 与驱动交互, 对 NPU 设备 AI Core 实施执行控制 (暂停/单步/恢复)。
7. Preload 库劫持 runtime 关键调用 (SetDevice / Register Kernel Object / Launch Kernel Object), 把进程标识信息回送 Server。
8. 用户在断点命中等时刻可使用变量/寄存器/内存打印、调用栈回溯、上下文切换 (AI Core 间或 simt vf 内线程间)、状态信息展示 (AI Core / Block / Device / Task / Stream / Thread) 等查询能力。

**性能/数据相关 (原文)**:
- 硬断点上限: **4 个**, 仅 simt vf / simd vf 可用。
- 芯片覆盖: 910B、950、310P。
- 调试通道: `/proc/debug_switch` (写 `1` 开启)。
- 驱动依赖: **NPU Driver v26.0+**。
- 编程语言与平台: C++ (核心引擎), Linux Host。

**关键风险点 (原文第 5 节)**: 当前依赖 Simt/Simd VF 函数且必须 `-O0`, 局部代码行可能无法断住。

| 场景描述 | 功能清单 | 功能描述 | 限制 |
| --- | --- | --- | --- |
| 程序控制 | 断点设置 | 软、硬断点增删管理，其中硬断点只用于simt vf/simd vf | 硬断点只用于simt vf/simd vf, 个数不超过4个 |
| 程序控制 | 单步调试 | step over: 代码行级别单行往下运行; step in: 进入函数 ; step out: 跳出函数 | NA |
| 程序控制 | 恢复运行 | 用于命中断点后的恢复运行，让程序继续运行下去 | NA |
| 程序控制 | 中断运行 | 用于程序卡死在device侧时, 中断运行后查看卡死的代码行位置 | 中断后只支持查看调用栈和上下文切换功能 |
| 信息打印 | 打印变量 | 打印变量的内容，会根据变量类型展示对应的结构体成员, 支持在host代码上打印申请的GM变量内容 | 不支持表达式计算的打印 |
| 信息打印 | 打印寄存器 | 打印寄存器的内容 | NA |
| 信息打印 | 打印内存 | 打印不同类型的内存数据，包括UB,GM,L0A,L0B,L0C等 | NA |
| 信息打印 | 上下文切换 | AI Core之间切换，或者Simt vf 里的线程切换，与配合状态信息展示功能或程序控制类功能配合使用 | NA |
| 信息打印 | 状态信息展示 | 展示当前算子使用到的AI Core、Block、Device、Task、Stream、Thread等信息；展示当前AI Core停住位置的代码行信息 | NA |
| 信息打印 | 调用栈回溯 | 展示当前AI Core所在代码行的调用栈 | simt_vf, simd_vf下断点的调用栈不会展示main scalar上；main scalar上的调用栈不会展示出host侧代码 |
| core文件解析 | 信息打印场景所有功能 | 包含上述所有信息打印场景下的所有功能 | NA |

**逐行解读**:
- **断点设置**: 区分软/硬断点; 硬断点受 VF 单元与数量 (≤4) 双重约束, 表明硬件断点资源有限。
- **单步调试**: 三种语义 step over/in/out 与 CPU 调试一致, 适配算子函数调用层次。
- **恢复运行**: 用于命中断点后的连续运行, 关注多核同步场景下的恢复语义。
- **中断运行**: 针对设备侧卡死场景的"强制中断"机制, 但中断后能力受限 — 仅可看调用栈与切换上下文, 不能打印变量/寄存器/内存。
- **打印变量**: 类型感知的结构体成员展开; 支持 host 申请的 GM 变量; 不支持表达式 (如 `a+b`), 是功能边界。
- **打印寄存器**: NPU 特有寄存器可见性, 直接对照 CPU GDB 的 `info registers`。
- **打印内存**: 覆盖 NPU 关键存储层级 **UB / GM / L0A / L0B / L0C**, 是排查内存越界的核心手段。
- **上下文切换**: 在多 Core 与 Simt vf 线程间切换查看, 强调"配合使用" — 单看切换无意义, 需与状态/程序控制联用。
- **状态信息展示**: 同时给出"逻辑拓扑" (Core/Block/Device/Task/Stream/Thread) 与"代码位置" (停住行), 形成一张全局视图。
- **调用栈回溯**: 跨域栈展示存在**截断** — simt_vf/simd_vf 断点处不展示 main scalar 上的栈; main scalar 不展示 host 侧栈。这是 AI Core 多执行单元带来的栈分段现实约束。
- **core 文件解析**: 复用信息打印场景的全部能力, 表明 core dump 走的是同一套数据通路。

### 表 2 — 第 4 节测试设计表 (逐字还原)

| 测试类型 | 算子场景 | 描述 | 示例 |
| --- | --- | --- | --- |
| 单元测试 | NA | 测试Server测功能函数 | HandleStubDevice测试能否处理收到的device_id信息 |
| E2E测试 | Simt算子 | 测试上述所有功能是否成功 | 断点设置在simt算子里，能否恢复运行，变量打印等功能 |
| E2E测试 | Simd算子 | 测试上述所有功能是否成功 | 断点设置在simd算子里，能否恢复运行，变量打印等功能 |

**逐行解读**:
- **单元测试**: 范围仅覆盖 Server 侧功能函数 (如 `HandleStubDevice` 对 device_id 的处理), 即对劫持库上报的数据通路做最小单元验证。
- **Simt E2E**: 在 Simt 算子中跑完整闭环 (断点 → 恢复 → 变量打印), 验证 SIMT 执行模型下的多线程调试语义。
- **Simd E2E**: 同上但面向 SIMD 向量算子, 侧重 SIMD lane 维度的可观测性。
- **Cube E2E**: 覆盖 Cube (矩阵乘) 算子场景, 注意描述栏写的是"断点设置在 simd 算子里" — 疑似原文笔误 (与算子场景列不一致), 但 cube 算子调试复用同一套功能集合。
- **缺失项**: 未列出集成测试 (Integration Test), 仅 UT 与 E2E 两类。

## 【使用方法】

依据原文第 3.4.3 节"使用说明":

**前置条件**:
1. 操作系统: **Linux Host**。
2. 驱动版本: **NPU Driver v26.0+**。
3. 用户权限: **root** (用于打开驱动调试通道)。
4. 算子二进制必须含 **`-g -O0`** 编译选项 (保留 DWARF 调试符号)。

**启用步骤 (原文命令)**:
```bash
# 1. 编译算子时保留调试信息
# 确保编译时加入 -g -O0 选项保留调试符号

# 2. 打开驱动调试通道 (需 root)
echo 1 > /proc/debug_switch

# 3. 启动调试器
msdebug <app>

# 4. 进入交互界面后设置断点并运行
b <file_name>:<line_no>   # 设置断点
run                       # 启动被调试程序
```

**关键交互命令 (依表 1 功能映射)**:
- 断点管理: `b <file>:<line>` (增) / 对应 `delete` 类 (删)
- 单步: `step over` / `step in` / `step out`
- 恢复运行: `continue` (命中断点后)
- 中断运行: 用于设备侧卡死场景 (功能入口未给出具体命令)
- 信息打印: `print` (变量/寄存器/内存)、`bt` 或等价 (调用栈)、`info` (状态信息)、`thread/core switch` (上下文切换)

> 注: 原文仅显式给出 `b` 与 `run` 两条命令; 其余命令为表 1 功能描述映射的常见 LLDB 用法, **具体命令字符串原文未涉及, 需参照 LLDB 上层语法**。
