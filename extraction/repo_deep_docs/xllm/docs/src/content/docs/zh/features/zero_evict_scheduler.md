# xLLM Zero Evict 调度器 — 一体化深度解读

---

## 【定位】
本文档介绍 xLLM 推理引擎中 **zero_evict 调度策略**：一种以"最小化请求淘汰率"为核心目标的调度算法，从而减少被淘汰请求带来的 prefill 重计算开销、降低 TPOT 时延。

---

## 【技术要点】

1. **策略定位**：zero_evict 是一种调度算法（而非模型或硬件特性），其首要目标是把"请求淘汰"的发生概率降到最低。
2. **核心收益**：通过避免请求被淘汰，**减少被淘汰请求的 prefill 计算量**，并直接降低 **TPOT（Time Per Output Token）**。
3. **调度判定机制**：在调度一个请求前，先**模拟该轮次（simulating rounds）**，检测"接受此请求后是否会引发对其他请求的淘汰"，只有不会引发淘汰时才真正调度。
4. **开关方式**：功能已落地于 xLLM，对外通过 **gflag 参数**控制启停；无侵入式 API 调用，遵循 xLLM 通用启动配置范式。
5. **关键配置参数**：
   - `--use_zero_evict=true`：启用 zero_evict 策略；
   - `--max_decode_token_per_sequence=256`：限制每个序列最大 decode token 数（与调度策略配合使用）。
6. **验证场景**：文档以 **Qwen3-8B** 模型、在 **E2E 时延受限**条件下给出了量化收益。

---

## 【关键机制与数据】

**工作原理（原文）**：
> "这种调度算法通过模拟轮次，检测请求是否调度可以被调度且不导致其它请求被淘汰。"

即调度器在"决策窗口"内做一次前瞻式仿真：
- 输入：当前等待队列 + 已运行序列的 decode 进度；
- 动作：假设加入候选请求，跑一遍调度轮次；
- 判定：若接受后**不会导致**其他正在运行的请求因显存/序列长度上限被淘汰，则放行；否则拒绝该请求以避免后续连锁淘汰。

**收益链条（原文逻辑推导）**：
```
淘汰减少 → 不必重新 prefill 已生成的请求 → prefill 计算量下降 → TPOT 下降
```
即 zero_evict 并不直接优化算子，而是通过"保住序列不被踢出批"的间接方式，让已 prefill 完成的 token 不需要重做，从而摊薄每 token 的解码代价。

**性能数据（原文）**：
- 模型：Qwen3-8B
- 约束条件：限制 E2E 时延
- 结果：**TPOT 时延下降 27%**

## 【使用方法】

原文给出的启用方式如下，需在 xLLM 启动参数中同时配置以下 **gflag**：

| 参数 | 取值 | 作用 |
|---|---|---|
| `--use_zero_evict` | `true` | 开启 zero_evict 调度策略 |
| `--max_decode_token_per_sequence` | `256` | 设置每个序列允许的最大 decode token 数 |

```
--use_zero_evict=true
--max_decode_token_per_sequence=256
```
