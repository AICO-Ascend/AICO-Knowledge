# 多模态支持文档 · 一体化深度解读

## 【定位】

本篇文档系统描述 xLLM 推理引擎在**多模态推理能力上的当前支持范围与边界**,帮助用户快速判断 xLLM 是否能直接服务其多模态业务(选型参考),并在使用时避开尚未完成的关键能力(如 prefix cache、chunk prefill)。

## 【技术要点】

1. **支持的视觉语言模型(VL 系列)**:覆盖四大家族 —— Qwen2.5-VL(7B/32B/72B)、Qwen3-VL(2B/4B/8B/32B)、Qwen3-VL-MoE(A3B/A22B)、MiniCPM-V-2_6(7B),规模从 2B 到 72B,涵盖稠密与 MoE 两种架构。
2. **图像输入组合方式**:支持**单图输入、多图输入、图片+Prompt 组合、纯文本 Prompt** 四种形态,覆盖多模态对话的主流用法。
3. **图片编码方式**:同时支持 **Base64 内联**与**图片 URL** 两种数据送入方式,方便对接前端直传与对象存储外链。
4. **ChatTemplate 渲染机制**:xLLM **统一基于 JinJa 渲染 ChatTemplate**;部署 MiniCPM-V-2_6 时,模型目录**必须提供 ChatTemplate 文件**才可正常运行。
5. **已知限制(未完成项)**:多模态后端**不支持 prefix cache** 与 **chunk prefill**,官方明确标注"正在支持中";视频、音频等其他模态**正在推进中**。
6. **模态成熟度**:当前主要落地为**图片模态**,视频/音频仍处于规划与研发阶段。

## 【关键机制与数据】

- **模型覆盖矩阵(原文)**:Qwen2.5-VL(7B/32B/72B)、Qwen3-VL(2B/4B/8B/32B)、Qwen3-VL-MoE(A3B/A22B)、MiniCPM-V-2_6(7B)。这反映了 xLLM 当前对**Qwen 系列 VL 生态的深度适配**,以及通过 MoE 变体覆盖更大有效参数量场景的策略。
- **图片输入路径(原文)**:Base64(适合客户端直传,减少网络跳转)+ 图片 URL(适合存放在 OSS/COS 等的对象存储,降低请求体大小)。
- **Prompt 组合(原文)**:纯文本 Prompt 仍可独立使用,意味着多模态后端**不会强制要求附带图片**,具备纯文本 fallback 能力。
- **ChatTemplate(原文)**:JinJa 渲染是**统一机制**,意味着所有多模态模型(不仅 MiniCPM-V-2_6)都走 JinJa 模板管线,但只有 MiniCPM-V-2_6 被**强制要求**自带模板文件 —— 这是该模型相对其他模型的特殊依赖。
- **能力缺口(原文)**:prefix cache(前缀缓存,可显著降低重复 system prompt + 长图片描述 token 的重复计算)与 chunk prefill(分块预填,缓解长多模态输入首字延迟)在多模态后端**尚未生效**,使用时需要理解这两项优化对吞吐与 TTFT 的影响将被关闭。

## 【表格解读】

原文无表格。但原文中"支持模型"部分以**列表形式枚举了模型族与规模**,可整理为等价表格以便对照:

| 模型族 | 规格(规模/变体) |
|---|---|
| Qwen2.5-VL | 7B / 32B / 72B |
| Qwen3-VL | 2B / 4B / 8B / 32B |
| Qwen3-VL-MoE | A3B / A22B |
| MiniCPM-V-2_6 | 7B |

逐行解读:
- **Qwen2.5-VL(7B/32B/72B)**:覆盖消费级单卡到多卡大模型部署三档典型规模。
- **Qwen3-VL(2B/4B/8B/32B)**:相较 Qwen2.5-VL 增加了 2B/4B 等小尺寸档位,适配边缘与低显存场景。
- **Qwen3-VL-MoE(A3B/A22B)**:MoE 变体,A 前缀为阿里系对"激活参数"标注,可在显著低于稠密模型推理成本下获得大容量模型效果。
- **MiniCPM-V-2_6(7B)**:第三方模型,特殊点是**必须自带 ChatTemplate**,部署时需检查模型目录。

## 【关联】

文末未给出内部链接,因此无法直接从本文档推导与仓库其他模块的引用关系。但根据文中提及的关键词,可以推断以下**隐含的上下游/对偶模块**关联(基于原文事实,不做外延扩展):

- **JinJa ChatTemplate 渲染**:这是 xLLM 的**统一模板渲染机制**,意味着本文档的 ChatTemplate 行为与其他模型部署文档(纯文本 LLM 部署类文档)共享同一渲染管线。
- **prefix cache / chunk prefill**:这两项能力在多模态后端**未启用**,而它们通常属于推理引擎的**通用性能优化模块**,因此在纯文本 LLM 路径下大概率是可用状态;多模态用户在使用时需理解该差异。
- **图片模态 → 视频/音频模态**:原文明确"视频、音频等模态正在推进中",说明多模态后端存在**模态注册/扩展点**,后续视频/音频能力将沿同一管线加入。
- **Base64 与 URL 输入**:这两种输入形态通常对应 xLLM 的**HTTP/RPC 接口层**的协议适配,意味着客户端 SDK 与服务端协议需要兼容多模态 schema。

## 【使用方法】

原文未给出具体的配置项、命令行参数或启用开关。可从原文提取的**部署/使用约束**如下:

1. **选择模型**:在 Qwen2.5-VL、Qwen3-VL、Qwen3-VL-MoE、MiniCPM-V-2_6 中按规模与场景挑选。
2. **图片输入准备**:准备 Base64 编码或可访问的图片 URL,选择对应输入方式提交。
3. **Prompt 形态**:可组合 单图 / 多图 / 图片+Prompt / 纯文本 Prompt。
4. **MiniCPM-V-2_6 特殊要求**:模型目录下**必须提供 ChatTemplate 文件**,否则基于 JinJa 的统一渲染管线将无法完成模板填充。
5. **能力边界预期**:不要依赖 prefix cache 与 chunk prefill 的多模态优化(尚未生效);暂勿尝试视频/音频输入(尚未支持)。
