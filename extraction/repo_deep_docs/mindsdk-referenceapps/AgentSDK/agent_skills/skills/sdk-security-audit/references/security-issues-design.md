# 一体化深度解读：安全设计规范

## 【定位】

本文档是 SDK 安全审计场景下的一份**安全设计规则集与审计清单**，参考华为昇腾社区安全设计规范，为审计人员列出在个人数据保护、系统接入、系统本体、数据传输、密码学五大维度上需要核查的规则、危险模式与检查项，用于评判 SDK 是否符合安全设计基线。

---

## 【技术要点】

1. **五大规则域 + 14 条规则**：文档以表格形式列出 14 条安全规则（编号 1.1–1.4、2.1–2.2、3.1–3.4、4.1–4.2、5.1–5.3），覆盖个人数据（4 条）、系统接入（2 条）、系统安全（4 条）、数据传输（2 条）、密码学（3 条）五个安全域，每条规则标注风险等级（高 / 极高）。
2. **风险等级分级**：极高风险包括规则 1.4（个人数据传出客户网络）、2.1（所有管理接口必须有接入认证）、2.2（禁止凭据包含在发布软件包）、3.3（禁止日志打印敏感信息）、5.2（禁止使用已被破解的密码学算法）。其余均为高风险。
3. **危险模式清单（Anti-patterns）**：明确列出 4 类共 11 种"绝对禁止"模式——认证相关 3 种、权限相关 2 种、加密相关 5 种、数据保护相关 4 种（其中"日志打印敏感信息"在两表中重复出现 1 次）。
4. **明确禁止的弱密码学对象**：DES、MD5、RSA 1024、TLS 1.0 四类算法/协议被点名禁止（规则 5.2 及"加密相关"危险模式）。
5. **明确推荐的随机数源**：`RAND_bytes`（OpenSSL）、`/dev/random`（类 Unix）、`/dev/urandom`（Linux Kernel 5.18 及其之后的版本）（规则 5.3）。
6. **明确推荐的传输安全协议**：IPSec、MACSec、HTTPS（规则 4.2）。
7. **审计检查清单**：提供 4 大类共 13 个 checkbox 项，覆盖个人数据保护、认证安全、系统安全、数据传输安全、密码学安全 5 个检查维度。

---

## 【关键机制与数据】

本文档为审计规范而非技术实现文档，不存在工作原理、数据流、性能数据等内容。所有"机制"均以**规则条文 + 风险等级**形式呈现，列举如下（原文摘录）：

- **原文：** "所有管理接口必须有接入认证机制……禁止存在绕过正常认证机制直接进入系统进行系统管理的隐秘管理通道"——核心机制是"认证覆盖完整性"。
- **原文：** "禁止将认证凭据（如口令/密码/私钥等）包含在发布的软件包中"——核心机制是"凭据与代码分离 + 凭据可修改 + 加密存储"。
- **原文：** "对外服务应使用系统低权限账号运行，不应使用'root'等特权账号运行"——核心机制是"最小权限原则"。
- **原文：** "产品对外发布的各类软件或独立AI软件包，需具备完整性校验机制（如数字签名，或者哈希值校验等）"——核心机制是"数字签名/哈希校验"。
- **原文：** "系统应支持使用通用加密通道传输，或者支持将机密数据加密后再传输。建议系统缺省部署和开启这些安全机制"——核心机制是"加密通道 + 默认开启"。
- **原文：** "应该是密码学意义上的安全随机数。例如：RAND_bytes（OpenSSL）、/dev/random文件（类Unix）、/dev/urandom文件（Linux Kernel 5.18 及其之后的版本）"——核心机制是"CSPRNG"。
- **术语定义原文：** "**个人数据**：……匿名化后的数据不属于个人数据。假名化后的数据仍属于个人数据。**敏感个人数据**：……包括生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹等信息，以及未成年人的个人信息"——明确区分"个人数据"与"敏感个人数据"的边界（匿名化 ≠ 假名化）。

## 【表格解读】

文档共有 **15 张结构化表格**（5 大规则域 14 条规则表 + 1 张危险模式表，下面选取核心表格逐字还原）。

### 表 1：个人数据保护规则（1.1–1.4）

| 规则编号 | 规则名称 | 风险等级 | 说明 |
|---------|---------|---------|------|
| 1.1 | 个人数据的搜集和处理需要获得用户本人同意 | 高 | 获取敏感个人数据或者对用户画像时需获得用户的单独同意。应至少在产品的客户手册等客户面资料中说明搜集的个人数据的范围、用途、保护措施、存留期等，并在发生变更时及时更新上述说明 |
| 1.2 | 个人数据的搜集需遵循最小化原则 | 高 | 禁止搜集不必要的个人数据 |
| 1.3 | 个人数据应该加密存储并提供安全保护机制 | 高 | 个人数据应该加密存储，并提供必要的安全保护机制（如访问权限控制、访问日志记录等）；存储的个人数据超过声明的存留期后应立即删除 |
| 1.4 | 禁止未经授权将个人数据传出客户网络 | 极高 | 禁止未经授权将个人数据传出客户网络；禁止个人数据跨境转移 |

**解读**：四规则构成个人数据全生命周期治理闭环——搜集阶段（1.1 同意 + 1.2 最小化）→ 存储阶段（1.3 加密 + 访问控制 + 留存期自动删除）→ 传输阶段（1.4 极高风险，禁止出网 + 禁止跨境）。注意 1.4 是该域中**唯一**的"极高"风险等级项，反映"数据出境"是合规红线。

---

### 表 2：系统接入安全规则（2.1–2.2）

| 规则编号 | 规则名称 | 风险等级 | 说明 |
|---------|---------|---------|------|
| 2.1 | 所有管理接口必须有接入认证机制 | 极高 | 所有能对系统管理的人机接口以及机机接口必须有接入认证机制，禁止存在绕过正常认证机制直接进入系统进行系统管理的隐秘管理通道 |
| 2.2 | 禁止将认证凭据包含在发布的软件包中 | 极高 | 禁止将认证凭据（如口令/密码/私钥等）包含在发布的软件包中，所有接入认证凭据都必须支持修改，建议支持加密存储这些认证凭据 |

**解读**：两条均为极高风险，覆盖"认证入口完整性 + 凭据生命周期"。2.1 强调**接口层面**不可有隐藏后门（含人机接口 + 机机接口），2.2 强调**凭据层面**不可硬编码、必须可改、建议加密存储。

---

### 表 3：系统安全规则（3.1–3.4）

| 规则编号 | 规则名称 | 风险等级 | 说明 |
|---------|---------|---------|------|
| 3.1 | 安全方案设计要遵从操作系统的安全框架 | 高 | 安全方案设计要遵从操作系统的安全框架，不要违反系统现有的安全设计原则，不要破坏系统原有安全框架 |
| 3.2 | 对外服务应使用系统低权限账号运行 | 高 | 产品对外提供能够被远程访问的服务和进程，应使用系统低权限账号运行，不应使用"root"等特权账号运行 |
| 3.3 | 禁止在日志、调测信息中打印敏感信息 | 极高 | 禁止在日志、调测信息中打印口令、秘钥等敏感信息 |
| 3.4 | 对外发布的软件需具备完整性校验机制 | 高 | 产品对外发布的各类软件或独立AI软件包，需具备完整性校验机制（如数字签名，或者哈希值校验等） |

**解读**：3.1 是"不要重复发明轮子、不要破坏 OS 原生安全"的元规则；3.2 与 3.3 分别从**权限纵深防御**与**信息泄漏面**两端收紧；3.4 强调供应链完整性（数字签名 / 哈希校验）。

---

### 表 4：数据传输安全规则（4.1–4.2）

| 规则编号 | 规则名称 | 风险等级 | 说明 |
|---------|---------|---------|------|
| 4.1 | 机密数据传输应使用加密通道 | 高 | 在不同实体、节点或者网络之间传递机密数据（如个人数据、口令或秘钥、运营业务关键数据等）时，若存在泄漏风险，系统应支持使用通用加密通道传输，或者支持将机密数据加密后再传输。建议系统缺省部署和开启这些安全机制 |
| 4.2 | 使用业界标准的传输安全协议 | 高 | 使用安全传输通道保护数据时，建议使用业界标准的传输安全协议（如IPSec、MACSec、HTTPS等） |

**解读**：4.1 是"必须加密 + 默认开启"的策略要求；4.2 给出具体协议清单（IPSec/MACSec/HTTPS）。两者是"策略层"与"实现层"的对应关系。

---

### 表 5：密码学安全规则（5.1–5.3）

| 规则编号 | 规则名称 | 风险等级 | 说明 |
|---------|---------|---------|------|
| 5.1 | 使用业界公开的、标准的密码学算法 | 高 | 系统中应该使用业界公开的、标准的密码学算法，和使用经过权威机构（如ISO、RFC等）推荐或认可的密码学算法库 |
| 5.2 | 禁止使用已经被破解的密码学算法和协议 | 极高 | 禁止使用已经被破解的、或者存在严重安全漏洞的密码学算法和协议，如禁止使用被破解的DES、MD5等算法，禁止使用 RSA 1024 低秘钥强度算法，禁止使用TLS1.0等被破解的安全协议等。当这些不安全密码学算法和协议用于非安全用途时可不遵守本条要求 |
| 5.3 | 密码算法中使用的随机数必须是安全随机数 | 高 | 密码算法中使用的随机数，必须是密码学意义上的安全随机数。例如：RAND_bytes（OpenSSL）、/dev/random文件（类Unix）、/dev/urandom文件（Linux Kernel 5.18 及其之后的版本） |

**解读**：5.1 是"算法来源可信"原则；5.2 是"黑名单禁用"原则，并给出**例外条款**——弱算法用于非安全用途时可不受限；5.3 限定了**可接受**的 CSPRNG 实现（注意 `/dev/urandom` 仅在 Linux Kernel 5.18+ 才被视为密码学安全）。

---

### 表 6：危险模式清单（合计 4 类 11 行）

| 模式 | 风险等级 | 说明 |
|------|---------|------|
| 硬编码密码/密钥 | 极高 | 代码中包含硬编码的认证凭据 |
| 绕过认证的后门 | 极高 | 存在可绕过正常认证的隐秘通道 |
| 默认密码 | 高 | 使用默认密码且不支持修改 |
| root/特权用户运行服务 | 高 | 对外服务使用特权账号运行 |
| 不必要的文件权限 | 高 | 文件权限设置过于宽松 |
| 使用DES加密 | 极高 | DES已被破解，不安全 |
| 使用MD5哈希 | 极高 | MD5已被破解，不安全 |
| 使用RSA 1024 | 极高 | RSA 1024密钥强度不足 |
| 使用TLS 1.0 | 极高 | TLS 1.0已被破解 |
| 使用伪随机数 | 高 | 安全用途使用非密码学安全随机数 |
| 明文存储个人数据 | 高 | 个人数据未加密存储 |
| 明文传输敏感数据 | 高 | 敏感数据未加密传输 |
| 日志打印敏感信息 | 极高 | 日志中包含口令、密钥等 |

**解读**：表中"加密相关"包含 5 行（DES/MD5/RSA 1024/TLS 1.0/伪随机数），其中 4 项"极高"、1 项"高"；"认证相关"3 项（2 极高 + 1 高）；"权限相关"2 项（均高）；"数据保护相关"4 项（1 极高 + 3 高）。"日志打印敏感信息"在本表与规则 3.3 表中**重复出现**，体现其作为横切关注点的高优先级。

---

### 表 7：审计检查清单（5 类 13 项 checkbox）

| 检查维度 | 检查项 |
|---|---|
| 个人数据保护 | ① 个人数据搜集是否获得用户同意？② 是否遵循最小化原则？③ 是否加密存储？④ 是否存在未经授权的传输？ |
| 认证安全 | ⑤ 所有管理接口是否有认证机制？⑥ 是否存在硬编码凭据？⑦ 凭据是否支持修改？ |
| 系统安全 | ⑧ 服务是否使用低权限账号运行？⑨ 日志中是否包含敏感信息？⑩ 软件是否具备完整性校验机制？ |
| 数据传输安全 | ⑪ 机密数据传输是否使用加密通道？⑫ 是否使用标准传输安全协议？ |
| 密码学安全 | ⑬ 是否使用标准密码学算法？是否使用已被破解的算法（DES、MD5、RSA 1024、TLS 1.0）？是否使用安全随机数？ |

**解读**：检查清单是规则表（做什么）与危险模式表（禁什么）的**审计入口**，将规则条款转化为可逐项打勾的核查动作。注意"密码学安全"维度在原文中只有 1 个 checkbox 节点，但内含 3 个并列子问题。
